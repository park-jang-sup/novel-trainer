## 2. 무엇이 문제였나 — 축이 아니라 자리였다

세션 9 §5 의 진단은 맞았다. `seed_data.sql` 의 문자열 리터럴 안에 **실제 줄바꿈
176개**가 들어 있었고, Supabase 편집기가 붙여넣기에서 그것을 CRLF 로 바꿨다.

```
덤프 전체의 줄바꿈            176개 / 32필드
그 32필드                     mo-* 8문항(instr 8 + pass 3) · pv-* 8문항(instr 10 + pass 1)
seed_data.sql 의 실제 줄바꿈   176개 — 정확히 같다
```

고친 곳은 `sqlStr` 한 함수다. **줄바꿈이 든 값만** `E''` 로 낸다.

```
전부 E'' 로 바꾸면   77행이 통째로 diff 가 되어 읽을 수 없다
줄바꿈 있는 것만     32 insert / 208 delete. 바뀐 리터럴이 딱 32개
```

`seed_check.sql` 이 안 바뀌는 것이 검산이다 — 그 파일에는 원문이 없고 md5 와
길이뿐이고, md5 는 **덤프 문자열**에서 뽑는다. SQL 표기를 바꿔도 안 움직인다.
**바뀌었다면 md5 계산 경로까지 건드린 것이다.**

### 이제 세 겹이다

```

test:scoring    커밋된 SQL 네 개를 본다        커밋할 때
seed_check.sql  덤프와 DB 를 대조한다          적용한 뒤
```

가운데가 비어 있었다. 세션 9 §6-1 이 짚은 그대로다.


### `E''` 는 줄바꿈 있는 값에만 쓴다

`sqlJsonb` 는 안 건드렸다. `JSON.stringify` 가 줄바꿈을 이미 `\n` 두 글자로
만들어서 SQL 안에 실제 줄바꿈이 안 생긴다. **덤프 전체의 역슬래시가 0건**이라
평범한 `''` 로도 맞는다. 이 전제가 깨지면(덤프에 역슬래시가 들어오면) 다시 재라.

## 4. 스캐너의 미탐 둘 — 알려진 한계로 적을 것이 아니었다

**이번 세션에서 가장 값진 것이다.**

첫 지시서의 스캐너는 `--` 줄주석만 다뤘다. 다른 자리에서 그것을 여덟 표본 밖으로
밀어 보고 두 군데를 찾았고, **알려진 한계로 주석에 적어 두자**는 제안이 왔다.
재보니 둘 다 **과탐이 아니라 미탐**이었다.

```
/* 가 ' 나 */ select '다⏎라';     count 0   ← 주석의 따옴표가 상태를 뒤집어 삼켰다
select type'가\⏎나';              count 0   ← e 로 끝난 식별자를 E'' 로 오인
```

과탐이면 시끄럽게 죽어서 알았을 것이다. 둘 다 **조용히 통과**했다.

```
이 함수가 하는 일은 '없음을 증명하는 것' 하나뿐이다.
그래서 과탐보다 미탐이 훨씬 나쁘다. 없음을 재는 자가 조용히 틀리면 아무도 모른다.
```

지금 저장소에는 둘 다 없다(블록 주석 0건, 오인 0/1416). 그래도 고쳤다. 고친 뒤에도
진짜 `E''` 판정은 32개 그대로라 **오늘의 출력에 영향이 0이다.**

세션 9 §4 의 '내용 통째 교체'와 방향이 반대다. 저기는 검사를 조이면 오탐이 함께
느는 **거래**가 있어서 한계로 남겼다. 여기는 거래가 없었다 — 고쳐도 출력이 안 바뀐다.
**거래가 없으면 한계로 적을 이유가 없다.**

### 겉보기 수가 맞아서 더 위험했던 자리

따옴표 하나짜리 여러 줄 블록 주석은 `count` 가 1로 **맞게** 나왔다. `lines` 를 보니
1행이었는데 진짜 위반은 2행이었다. 과탐 1 + 미탐 1 이 상쇄된 것이다.

**수가 맞는 것은 검사가 일한다는 증거가 아니다.** 이 세션 내내 같은 이야기다.

### 줄주석을 블록 주석보다 먼저 봐야 한다

`-- 원본: seed/dump/*.json` 의 `/*` 가 블록 주석 시작으로 잡힌다. 저장소의 `/*`
둘은 실제로 **전부 `--` 안의 글자**였다. 순서를 바꾸면 `gen:seed` 가 이유 없이 죽는다.

## 5. 이스케이프 순서 — 스캐너로는 안 잡히는 자리

```
정상        value.replace(\\ → \\\\).replace(' → '').replace(⏎ → \n)
뒤집으면    value.replace(⏎ → \n) …그다음 역슬래시 치환이 그것을 \\n 으로 만든다
```

```
E'가\n나'    PG 가 읽으면  "가⏎나"     진짜 줄바꿈
E'가\\n나'   PG 가 읽으면  "가\n나"     역슬래시와 n 두 글자
```

**SQL 안에 실제 줄바꿈이 없으므로 스캐너는 0개로 통과한다.** 왕복 디코더가
잡는다. 그것이 verify.ts 블록에 `decodeSqlLiteral` 이 있는 이유다.

## 6. 물기 시험 — 검사가 실제로 무는지 재라

지시서의 목표 수가 다 맞았다는 보고를 받았다. 그런데 **그 수는 지시서에 미리 박아
둔 것이라, 맞는다는 사실 자체가 검사가 문다는 증거가 아니다.** 두 번 물려 봤다.

```
시험 1   옛 seed_data.sql 을 되돌린다   1250 / 17    파일 1 + 문항 16
시험 2   이스케이프 순서를 뒤집는다      1251 / 16    스캐너는 통과, 왕복 검사만 문다
```

두 감시가 서로 다른 것을 잡는다는 게 수로 나왔다. **다음 단계에서도 이걸 해라.**
검사를 새로 세우면 반드시 한 번은 병을 넣어 물리고 수를 적어라.

시험 2 는 손으로 고치기가 필요 없다. 이 스니펫이 모양에 안 기댄다.

```bash
cp lib/seed-sql.ts /tmp/seed-sql.bak
python3 - <<'PY'
import io, re, sys
p = 'lib/seed-sql.ts'
s = io.open(p, encoding='utf-8').read()
m = re.search(r"return `E'\$\{value\n(.*?)\}'`", s, re.S)
if not m:
    print(re.search(r'export function sqlStr.*?\n\}', s, re.S).group(0)); sys.exit(1)
lines = [l for l in m.group(1).split('\n') if l.strip()]
bs   = [l for l in lines if r'/\\/g' in l]
rest = [l for l in lines if r'/\\/g' not in l]
if len(bs) != 1 or len(rest) != 3:
    print(m.group(1)); sys.exit(1)
io.open(p, 'w', encoding='utf-8').write(s[:m.start(1)] + '\n'.join(rest + bs) + '\n' + s[m.end(1):])
print('순서를 뒤집었다')
PY
npm run gen:seed >/dev/null && npm run test:scoring | tail -2   # 1251 / 16
cp /tmp/seed-sql.bak lib/seed-sql.ts
npm run gen:seed >/dev/null && npm run test:scoring | tail -2   # 1267 / 0
```

## 7. 남은 일

### 7-0. 미결 — 붙여넣기 탐침 세 값 ★

DB 는 깨끗하다(`cr_남은_문항수 = 0`). 하지만 **편집기가 정말로 LF 를 CRLF 로
바꾸는지는 아직 직접 안 쟀다.** 세션 9 는 그것을 `instruction 217 → 227` 이라는
결과에서 거꾸로 추측했고, 세션 10도 결국 그 추측 위에서 고쳤다.

사람이 Supabase SQL 편집기에 **이 덩어리만 따로** 붙여 넣어 돌리면 된다.
psql 로 돌리면 뜻이 없다 — 재려는 대상이 편집기다.

```sql
select length(E'가\n나')  as e_문자열_3이어야_함,
       length('가
나')                     as 생_문자열_3인가_4인가,
       position(chr(13) in '가
나')                     as 생_문자열_CR_위치_0이어야_함;
```

```
3 · 4 · 2   세션 9 §5 의 진단이 실측으로 확정. 이 수를 여기 적어라
3 · 3 · 0   편집기가 바뀐 것이다. 그러면 오염의 원인이 다른 데 있다 — 멈추고 다시 재라
```

왼쪽(`E''`)은 어느 쪽이든 3이어야 한다. 그것이 이번에 고친 부분이다.

## 8. 이번 세션에서 틀린 것

### 8-1. 스캐너를 여덟 표본 밖으로 안 밀었다 ★

첫 지시서에서 스캐너 주석에 **"스캐너가 틀리면 아래 검사 전부가 거짓 통과다"**
라고 직접 써 놓고, 정작 그 스캐너를 표본 여덟 개 밖으로 뚫어 보지 않았다.
다른 자리에서 밀어 보고 두 군데를 찾았다.

```
검사를 새로 만들면 그 검사 자체를 뚫어 봐라. 4장의 둘은 그렇게 나왔다
```

세션 9 §7-1 과 같은 병의 다른 얼굴이다. 저기는 밴드가 검사를 대신 막고 있었고,
여기는 검사 자체가 조용히 뚫려 있었다. **둘 다 "통과"를 증거로 여긴 것이다.**

### 8-2. 사람에게 준 명령이 붙여넣기로 안 돌아갔다

시험 2 를 `# lib/seed-sql.ts 의 replace 네 줄을 손으로 옮기고` 라는 **주석**으로
써서 보냈다. 사람이 통째로 붙여 넣으니 그 줄이 그냥 주석으로 지나가고, 멀쩡한
코드로 `gen:seed` 가 돌아 1267/0 이 나왔다. **시험이 안 돌아간 것을 통과로 볼 뻔했다.**

그다음에 보낸 스니펫은 파일 원문을 그대로 매칭해서 `AssertionError` 로 죽었다.
클로드 코드가 쓴 글자가 내 시제품과 달랐다. **내가 안 본 것을 매칭에 걸었다.**

```
사람에게 보내는 것은 붙여넣기 한 번으로 끝나야 한다
모양에 기대는 매칭을 보내지 마라. 6장의 스니펫이 고친 판이다
```

### 8-3. 커밋 메시지에 수만 있고 근거가 없다

`a485cea` 에 `1250 / 17`, `1251 / 16` 은 적혔지만 `isE 0/1416` 도 블록 주석
미탐의 모양도 없다. **저장소만 보는 사람은 왜 그렇게 짰는지 모른다.**
그래서 이 문서가 있는 것이지만, 세션 9 §7-5 가 같은 자리에서 틀렸다.
