## 0. 작업 환경 — 세션 4에서 바뀐 것

세션 4 문서 0장(시드 세 파일, DB 덤프 단일 출처, Supabase 경고 처리)은

### 0-1. 두 서버를 띄우는 명령에 `&`가 빠져 있었다 ★

세션 3 문서 0-4를 그대로 붙여넣으면 uvicorn이 앞단을 잡아 뒤 명령이 안 돈다.
세션 5에서 실제로 겪었다 — 한 터미널에 통째로 붙여넣어 uvicorn이 bind 실패로
죽고 `npm run dev`만 실행됐다.

```bash
cd ~/projects/novel-trainer/scoring-server && source .venv/bin/activate
SCORING_SECRET=dev uvicorn main:app --port 8000 &
cd ~/projects/novel-trainer && npm run dev
```

이미 떠 있는지 확인하는 방법:

```bash
curl -s http://localhost:8000/healthz          # {"ok":true}
```

### 0-2. 환경변수 이름이 앱과 서버에서 다르다 ★★

```
앱   (.env.local)    SCORING_SERVER_URL  +  SCORING_SERVER_SECRET
서버 (uvicorn)       SCORING_SECRET
```

`remote.ts:16`이 `if (!url || !secret) return null`이다. **둘 중 하나만 있으면
오류 없이 조용히 null**이고 화면에는 "일부 검사는 문장 분석 서버가 연결되면
표시됩니다"만 뜬다. 세션 4가 형태소 서버를 "미배포"로 적은 것이 이 문구를 본
결과인데, 실제로는 uvicorn을 안 띄웠던 것일 가능성이 크다.

**환경변수는 Next dev가 시작할 때 한 번만 읽는다.** `.env.local`을 고쳤으면
반드시 재시작해야 한다. DB 변경은 요청마다 조회하므로 재시작이 필요 없다 —
이 둘을 헷갈리지 마라.

### 0-3. `selftest.py`가 접속 주소와 시크릿을 환경변수로 받는다


`SELFTEST_SECRET`도 같이 뺐다. 배포 뒤 실제 서버를 찔러볼 때 진짜 시크릿을
파일에 박아 커밋하는 사고를 막기 위해서다. **저장소는 세션마다 public으로
열린다는 것을 잊지 마라.**

### 2-2. 세션 4의 1순위 서술이 부정확했다 ★★

세션 4 문서 7장은 1순위를 "`verify.ts`를 53문항으로 넓힌다"로 적었다.
**넓히기만 하면 6단계는 여전히 초록불이다.**

당시 `verify.ts`의 검사 둘은 **양쪽 다 오탐만 본다.**

```
불변식 1   지문이 자기 forbidWords 에 걸리는가       → 6단계 지문은 이미 걸린다
불변식 2   어간이 흔한 단어의 접두사가 아닌가         → 좋은 답안이 막히는지만 본다
```

빠진 것은 범위가 아니라 **검사 종류**였다. "나쁜 답안이 통과하는가"를 보는
검사가 없었다. 실제로 6단계 금지 목록을 시각 묘사 20건으로 뚫어보니 **12건이
통과했다.**

**교훈: 검사에는 두 방향이 있다.** 오탐(좋은 답안이 걸린다)과 미검출(나쁜
답안이 통과한다). 초록불이 어느 쪽을 보고 있는지 확인하라.

### 2-3. 세션 3의 "10/10 검출"은 그 10건에 대해서만 참이었다

세션 3 문서 4-2가 `forbidWords` + `forbidLemmas` 병용 후 "10/10 검출"을

**손으로 확인한 표본은 반드시 테스트로 심어라.** 안 심으면 다음 사람이 그

## 4. 세션 5의 결정과 근거

### 4-1. `짙/VA`를 뺐다 ★

6단계는 시각을 막고 **청각·촉각·후각으로 쓰라는** 단계다. 후각 문장 6건을
시험했다.

```
걸림   냄새가 짙었다 / 쇳내가 짙게 배었다 / 향이 짙어 코끝이 얼얼했다
걸림   짙은 흙냄새가 코를 찔렀다 / 물비린내가 짙게 깔렸다 / 탄내가 짙어 숨이 막혔다
누출   그늘이 짙게 드리웠다 / 짙은 안개가 깔렸다
       (어둠이 짙었다 는 '어둠'이 이미 잡는다)
```

**6건 전부 오탐이고 시각 누출은 둘이다.**

세션 3의 4-6("오탐은 규칙으로 선언한다")이 **여기서는 안 통한다.** 선언으로
덮으려면 "짙다를 쓰지 마라"고 해야 하는데, 그건 이 단계가 쓰라고 요구하는
감각을 막는 것이다. **단계 목적과 정면으로 부딪치는 오탐은 선언으로 못 덮는다.**

이것이 4-6에 붙는 예외 조항이다. 오탐을 규칙으로 선언할 수 있는 조건은
"그 말을 안 써도 단계 목적을 달성할 수 있을 때"다.

### 4-2. `시야`를 넣은 것이 학습 효과 면에서 가장 크다 ★

지금까지는 `시선`만 막혀 있었다.

```
학습자   시선을 썼다  → ×
학습자   시야로 바꿨다 → ○
```

이 학습자가 배운 것은 감각 묘사가 아니라 **채점기 뚫는 법**이다. 훈련이
무효가 되는 게 아니라 반대 방향으로 훈련된다. `반짝했다`·`훤했다`·`선명했다`도
같은 구멍이었다.

### 4-3. 목록을 고치면 지시문도 같이 고친다 ★★

세션 3의 4-6은 "지시문에 선언하면 오탐이 아니라 제약이 된다"였다.
**그 논리가 성립하려면 선언한 것과 막는 것이 같아야 한다.** 목록만 늘리면
선언되지 않은 금지어가 늘고, 학습자에게는 그냥 오탐이다.

지시문 8개는 **뒤 두 문장이 글자 그대로 같았다.** 앞의 장면 설정만 다르다.
그래서 `replace()` 한 번으로 8개가 동시에 갈렸다. 실행 전에 확인한 것:

- 8문항 전부 그 문자열을 정확히 1회 포함하는가 → 8/8
- sensory 밖의 문항이 그 문자열을 갖고 있는가 → 없음 (번짐 없음)

**치환 전에 반드시 이 둘을 재라.** 하나라도 어긋나면 조용히 일부만 바뀐다.

새 지시문(45자 → 220자):

```
눈에 기대는 말을 걷어내고 다른 감각으로 다시 쓰시오.
눈·빛·색·시선·시야·모습·얼굴·그림자·어둠·캄캄·깜깜·컴컴·흐릿·뚜렷·선명·투명·
반짝·어른어른이 들어간 말은 전부 막습니다.
보다 계열(보이다·바라보다·살펴보다 등), 밝기와 색(밝다·어둡다·붉다·푸르다·
하얗다·검다·노랗다·흐리다·훤하다), 빛의 움직임(빛나다·번쩍이다·반짝이다·
어른거리다)도 막습니다.
```

**명사 18개는 전부 열거했다.** `forbidWords`는 어절에 문자열이 들어가기만 하면
걸리므로 학습자가 예측할 방법이 이 목록뿐이다. **용언 28개는 열거가 불가능하다** —
활용형이 무한하다. 대표어와 묶음 이름으로 냈다.

범주로 짧게 선언하는 안("눈으로 본 것을 가리키는 말은 전부 막습니다")은
버렸다. 짧고 목록 변경에 안 흔들리지만 학습자가 무엇이 걸릴지 미리 알 수 없어
4-6의 이득이 사라진다. **정확성이 길이보다 앞선다.**

### 4-4. 뚫기 표본은 개수가 아니라 범주로 잡는다 ★

목록은 끝내 완전해지지 않는다. 시각 어휘는 계속 나온다. **이 검사의 값은
완전성이 아니라 회귀 방지다.** 표본을 늘리면 지금 목록을 그만큼 부풀려야 하고,
그건 오탐을 늘린다.

6범주 15건으로 잡았다.

| | 범주 | 표본 | 근거 |
|---|---|---|---|
| ○ | 축약 불규칙 | 저고리가 하얘졌다 · 치마가 하얘지고 있었다 | `하얘지/VV`가 새 표제어로 굳는다 |
| ○ | `-어지다` 정상형 (대조군) | 하늘이 붉어졌다 · 방이 어두워졌다 | `VA + 어/EC + 지/VX`로 갈려 원래 잡힌다 |
| × | 태깅 붕괴 | 잎이 누레졌다 | `누/NNG 레/NNG`. 표제어가 안 나온다 |
| ○ | 미등재 형용사 | 형체가 흐려졌다 · 달이 훤했다 · 훤한 마당으로 나섰다 · 무늬가 선명했다 · 얼음이 투명했다 | 5-1·5-2 |
| ○ | MAG + 하다 | 물결이 반짝했다 · 물체가 어른어른했다 | `반짝이/VV`는 `반짝하다`를 못 잡는다 |
| ○ | 어휘 누락 | 시야가 좁아졌다 · 그는 시야를 돌렸다 | `시선`만 있었다 |
| × | 의도적 제외 | 윤곽이 드러났다 | `드러나다`는 시각 전용이 아니다 |

**`×` 둘은 성격이 다르다.** `누레졌다`는 **못 잡는 것**이고 `드러나다`는
**안 잡기로 정한 것**이다. 갈라 적어야 나중에 누가 "왜 안 잡지" 하고 목록에
넣는 일을 막는다. `드러나다`를 넣으면 "사실이 드러났다"·"어깨가 드러났다"가
전부 걸린다.

`누레졌다`를 잡으려고 `누`를 `forbidWords`에 넣으면 "누구·누나·누르다"가
전부 걸린다. **표제어가 아예 안 나오는 것은 보수 대상이 아니라 알려진 한계다.**

### 4-5. 태깅 사실과 판정 로직을 갈라 심는다 ★

`verify.ts`의 뚫기 표본은 `lemmas` 배열을 **박아둔 값**으로 검사한다.
Kiwi가 실제로 그렇게 태깅하는지는 TypeScript에서 확인할 방법이 없다.

```
selftest.py   Kiwi 가 '저고리가 하얘졌다'를 하얘지/VV 로 태깅한다   ← 태깅 사실
verify.ts     lemmas 에 하얘지/VV 가 들어오면 6단계가 못 잡는다    ← 판정 사실
```

`verify.ts`는 원래 이 방식이었다 — `emptyMorph({ lemmas: [{ lemma: '보',
tag: 'VV', surface: '봤다' }] })`가 손으로 박은 태깅이다. 새 방식을 들인 게
아니라 있는 것을 넓혔다.

**판정 로직을 Python에 다시 구현하지 마라.** `local.ts` 주석의 "규칙 기반
채점을 두 군데 두지 않는다"가 여기에도 적용된다.

**이득 하나**: `누레졌다`의 태깅 붕괴를 `selftest.py`에 "나오면 안 되는 것"으로
남겨두면, Kiwi가 이것을 고쳤을 때 그 검사가 실패하고 알려준다. **실패가 나쁜
소식이 아니라 좋은 소식인 유일한 검사다.** 그때 `누렇/VA-I`를 목록에 넣을 수
있게 된다.

### 4-6. 지시문 첫 문장만 제목으로 (`50ffd62`) ★

지시문이 220자가 되자 `<h1>` 하나에 담긴 굵은 글씨 여섯 줄이 화면을 덮었고,
실제 작업 대상인 원문 상자가 한 줄로 밀렸다.

**더 아픈 것은 세션 3의 4-7이 무력해진 것이다.** 그 결정은 "장면 설정을
`passage`에 넣으면 베껴서 통과하니 `instruction`에 둔다"였다. 그 설정이
금지어 목록에 삼켜졌다.

첫 문장을 제목으로 두는 것이 **53문항 전부에 맞는지** 확인하고 넣었다.

```
sensory            연못 바닥에 손을 넣은 상태다.              ← 장면
reduce_adverb      꾸미는 말을 걷어내고 다시 쓰시오.           ← 지시
emotion_action     '흥부는 기뻤다'를 감정어 없이 쓰시오.        ← 지시 (나머지 0자 → <p> 안 생김)
trim_padding       없어도 되는 문장을 지우고 다시 쓰시오.
adverb_exception   뒤 문장의 부사가 앞 문장 덕분에 값을 얻는 것을 고르시오.
```

**접는 UI는 넣지 않았다.** 금지 목록은 4-6에 따라 학습자가 반드시 읽어야 하는
선언이다. 접으면 안 읽고 들어가고, 그러면 선언이 아니라 오탐이 된다.

### 4-7. 목록의 번호와 통과 표식을 갈랐다 (`76477a6`) ★

번호 자리에 `○`를 넣고 있어 **통과할수록 목록이 망가졌다.**

```
전   1 ○ 3 ○ 5 ○ ○ 8      다섯 개를 통과하면 이렇게 된다
후   1  /  2 ○  /  3       번호 칸과 표식 칸을 나눈다
```

번호를 `--pass` 색으로 칠하는 안은 버렸다. **색만으로 알리면 색맹인 학습자에게는
아무 정보가 아니다.** `CheckRow`와 같은 활자 기호를 쓴다.

칸 폭은 번호 `2ch`, 표식 `1em`이다. `ch`는 mono에서 숫자 하나의 폭이라 문항이
10개를 넘어도 밀리지 않고, `1em`은 `CheckRow`의 관례다.

### 4-8. 라벨 자르기를 CSS에 넘겼다 ★

`LABEL_MAX = 40`이 실제 화면 폭과 안 맞아 어떤 줄만 두 줄이 됐다.
40을 30으로 낮추면 다른 줄이 불필요하게 잘린다.

**폭은 창 크기와 글꼴이 정한다. 글자 수로는 맞출 수 없다.**

증거가 화면에 나왔다. 40자 기준은 3번만 잘랐는데 `truncate`로 바꾸니 5번도
잘렸다 — 5번이 40자 미만인데도 폭을 넘고 있었다.

세션 3의 3-8("화면 문제는 화면을 보고 판단한다")과 같은 교훈이 되풀이됐다.

### 4-9. hybrid의 "통과"는 거짓 신호였다 (`bec064b`) ★★

`combine()`이 `needsAi`를 계산해 응답에 실어 보내는데 **`TrainClient`가 받아서
버렸다.** 화면이 쓰는 것은 `status`와 `morphAvailable`뿐이었다.

`hybrid`는 "규칙만으로는 판정이 끝나지 않는다"는 선언이다. AI 심사가 없는
상태에서 그냥 "통과"라고 쓰면 학습자는 자기 답안이 좋다고 배운다.
**실제로 지문을 절반 베낀 답안이 통과로 표시됐다.**

`morphAvailable`이 false일 때는 안내를 띄우면서 `needsAi`가 true일 때는 아무
말도 안 하는 **비대칭**이었다. 같은 종류의 미완성이므로 같은 크기·같은 색으로
낸다.

```
규칙 검사는 통과했습니다. 내용 심사는 아직 준비 중입니다.
```

**조건을 화면에서 다시 계산하지 않는다.** 응답의 `needsAi`를 그대로 믿는다.
판정 규칙을 두 군데 두면 갈라진다.

## 5. 확인한 사실 — 다시 재지 말 것

### 5-1. 같은 단어가 활용형에 따라 표제어가 갈린다 ★★

```
훤했다   →  훤하/VA
훤한     →  훤/XR + 하/XSA
```

`훤하/VA` 하나만 넣으면 `훤한`을 영원히 못 잡는다. **세션 3 문서 5-1의
"ㅂ불규칙은 한 표제어로 모인다"에 대한 반례다.** 모이지 않는 계열이 있다.

`forbidLemmas`에 **둘 다** 넣어야 한다. `훤/XR`을 넣어도 `훤칠한`은 안 걸린다 —
`훤칠/XR`이 한 덩어리이기 때문이다. `forbidWords`에 문자열 `훤`으로 넣으면
`훤칠한`이 걸린다. 실측으로 확인했다.

### 5-2. `NNG`·`XR` + `하/XSA` 계열은 `forbidLemmas`로 못 잡는다 ★

```
선명했다  →  선명/NNG + 하/XSA
투명했다  →  투명/NNG + 하/XSA
뚜렷했다  →  뚜렷/XR  + 하/XSA
```

`선명하/VA` 같은 표제어가 아예 나오지 않는다. `forbidWords`에 문자열로 넣는
수밖에 없다. **`뚜렷`이 처음부터 `forbidWords`에 있던 이유가 이것이었을 것이다.**

세션 3의 4-2("두 검사는 서로 다른 구멍을 메운다")에 세 번째 사례가 붙는다.

```
forbidLemmas 가 놓치는 것   복합어 · XR/NNG + 하 계열 · 축약 불규칙
forbidWords  가 놓치는 것   활용형
```

### 5-3. `-어지다`는 통째로 구멍이 아니다

```
붉어졌다    →  붉/VA + 어/EC + 지/VX          잡힌다
어두워졌다  →  어둡/VA-I + 어 + 지/VX          잡힌다
밝아졌다·검어졌다·노래졌다                      잡힌다
하얘졌다    →  하얘지/VV                       못 잡는다 (축약이 한 표제어로 굳음)
누레졌다    →  누/NNG + 레/NNG + 지/VV         태깅 자체가 깨짐
```

**축약 불규칙만 샌다.** 대조군 둘을 뚫기 표본에 남겨둔 이유다 — 나중에
"`-어지다`가 구멍"이라고 잘못 일반화하는 것을 막는다.

### 5-4. 6단계 금지 목록의 현재 성능

```
뚫기 표본 15건   →  13건 검출, 2건은 정상 실패
오탐 감시 13건   →  0건
좋은 답안 32건   →  막히는 것 2건 → 1건
```

좋은 답안 32건(청각 8 · 촉각 10 · 후각미각 6 · 온도균형 4 · 경계 4)으로
재보니 **목록이 38개에서 46개로 커졌는데 통과가 늘었다.** 짙 하나를 빼서 얻은
것이 아홉을 더해 잃은 것보다 크다.

남은 1건은 `흐리/VA` × "정신이 흐려 손끝이 떨렸다"다. 감각 묘사가 아니라 상태
서술이라 6단계에서 쓸 답안이 아니다. `reviewedCollisions`에 넣는다.

### 5-5. 6단계 지문 8개는 새 목록에서도 자기 검사에 걸린다

`seed_verify.sql` 불변식 2가 유지된다. `짙`을 뺐어도 8문항 전부 다른 금지어에
걸린다. **문항을 손대기 전에 이 검사를 미리 돌려봐라** — 깨지면 시드 전체가
롤백된다(세션 4의 2-5가 그 사례다).

### 5-6. `submissions`의 진도 표시는 과거 기록을 포함한다

1단계 목록의 `rm-heungbu-swallow`에 통과 표시가 붙어 있는데, 세션 5에서 제출한
답안은 미달이었다. 세션 2·3의 시험 기록이다. **채점 규칙을 고쳐도 과거 통과
기록은 남는다.**

### 5-7. 형태소 서버가 붙으면 화면에서 이렇게 갈린다

```
붙음   "통과"                        + 안내 문구 없음
안붙음 "일부 항목 확인 중"            + "…서버가 연결되면 표시됩니다"
```

`forbidLemmas`가 있는 문항이라면 형태소가 없을 때 `mergeForbidChecks`가
`pass + pending → pending`으로 떨어뜨린다. **결과가 "통과"로 뜨는 것 자체가
서버가 붙었다는 증거다.**

## 6. 알려진 결함 · 미확인

### 6-1. hybrid 6문항은 AI 심사 없이는 반쪽이다 ★

`@anthropic-ai/sdk`가 `package.json`에 있지만 **어디서도 import되지 않는다.**
`route.ts`는 `needsAi`를 계산해 응답에 실어 보내고 끝이다. TODO 둘(킬스위치,
한도 차감)도 미착수다.

`bec064b`로 거짓 신호는 없앴지만 그 자리에 **침묵을 넣었을 뿐**이다.
세션 5에서 두 답안을 제출했는데 화면에서 구별되지 않았다.

```
좋은 답안   까치가 금은보화 위치가 적힌 지도를 줬다. 그 사실에 눈이 커지고
            심장의 박동이 빨라지며 입꼬리가 살살 올라갔다.
베낀 답안   박이 갈라지고 안에서 금은보화가 쏟아졌다. 흥부의 얼굴에
            함박미소가 피었고 …
```

둘 다 "규칙 검사는 통과했습니다. 내용 심사는 아직 준비 중입니다."를 받는다.
규칙으로는 갈릴 수 없다 — `forbidWords`에 `미소`를 넣을 수는 없다.

**문항을 더 만들 때 hybrid를 늘리지 마라.** 늘릴수록 판정 없는 문항이 는다.
`golden_cases`가 7행뿐인 것(세션 3 대기표 4순위)도 여기 걸린다 — AI 프롬프트가
옳게 도는지 잴 골든셋이 convert 6문항이면 30행쯤 필요하다.

### 6-2. 긴 글 단계가 없어 기능 다섯이 논다 ★★

```
maxChars 있는 문항   38개   최소 33  중앙 42  최대 70
지문 길이            최소 11  중앙 44  최대 68
지문에 개행이 있는 문항   0 / 53
```

**53문항 전부 두세 문장이고, 하한(`minChars`)은 어디에도 없다.** 지금 커리큘럼이
훈련하는 것은 "짧게 쓰기" 하나다.

| 노는 기능 | 왜 안 얹혔나 |
|---|---|
| `maxProperNouns` | 근거가 "1화에 고유명사 넷 이상 금지"(작법정리 2부 18-3)다. **두 문장 지문에서는 잴 것이 없다** |
| `minChars` | 하한이 필요한 문항이 하나도 없었다 |
| `continue` 유형 | 이어 쓰기는 긴 글이다 |
| 개행 밀도 (세션 3 7-2 가) | 지문 53개 중 개행이 있는 것이 0개다 |
| 종결어미 다양화 (7-2 다) | 두 문장이면 종결어미가 둘이다. 다양화를 잴 수 없다 |

세션 3이 `maxProperNouns`를 구현해놓고(`ebbdc96`) 얹을 데를 못 찾아 대기표에
넣은 것, 7-2의 셋을 "채움률 60% 이후"로 미룬 것이 **전부 같은 원인이다.**
기능이 다섯 빠진 게 아니라 긴 글 단계가 없다.

붙일 자리는 비어 있다. **도입 트랙 4단계가 전부 문항 0이고, 4번이
`start_episode` "1화 축약"이다.**

**다만 지금 당장은 못 한다.** `maxChars`가 장치 노릇을 못 하고(세션 3 2-2 나),
AI 심사가 없어 긴 글은 갈리지 않는다. 6-1과 묶여 있다.

### 6-3. `verify.ts`가 파일 시스템에 의존하게 됐다

`seed/dump/problems.json`을 `readFileSync`로 읽는다. 경로가 `__dirname` 기준이라
`npm run test:scoring`으로는 문제없지만, 테스트 러너를 바꾸면 여기서 걸린다.
지금 막을 일은 아니고 알고 있으면 된다.

### 6-4. `convert-seeds.ts`가 덤프와 중복이다

`emotion_action` 6문항이 픽스처와 덤프 양쪽에 있고, `verify.ts`가 둘 다 검사한다.
세션 4 문서 7장 1순위가 정리 대상으로 지목했다.

**세션 5는 일부러 미뤘다.** 새 검사를 더하는 일과 옛 픽스처를 지우는 일을 한
지시서에 섞으면 테스트 수의 변화를 추적할 수 없다. `reviewedCollisions` 개념과
설계 근거 주석은 살려서 옮겨야 한다.

### 6-5. 형태소 서버가 배포되지 않았다

`SCORING_SERVER_URL`이 `localhost:8000`이라 로컬에서만 돈다. 배포하면 38문항이
실사용에서 살아난다.

**세션 5는 배포를 C 다음으로 미뤘다.** 근거: 서버가 서면 뚫린 구멍이 그 순간부터
실제 학습자에게 닿는다. 지금은 pending이 방패 노릇을 하고 있었다. 그물을 먼저
치는 쪽이 맞다. 이제 그물은 섰다.

배포에는 비용·인증·시크릿 관리가 붙고 검증이 화면이 아니라 배포 로그다.
다른 작업과 섞지 마라.

#### 새 문항을 넣는 절차 — 세션 4의 6장은 '고치는' 절차다 ★

세션 4 6-1은 `update`로 시작한다. 새로 넣을 때는 1번만 다르고 나머지는 같다.

1. **DB에 넣는다.** `stage_id`는 박아 넣지 말고 `skill_key`로 조회한다 —
   `id`와 `order_no`는 무관하고 재구축하면 `id`가 달라진다

   ```sql
   insert into problems
     (stage_id, type, scoring_mode, instruction, passage, choices, scoring_config,
      source_tag, genre_tag, tone_tag, difficulty, source_key)
   values (
     (select id from stages where skill_key = 'rhythm'),
     'remove', 'auto', '...', '...', null, '{...}'::jsonb,
     null, 'fantasy', null, 1, 'rh-heungbu-yard'
   );
   ```

   **`source_key`는 반드시 넣는다.** 유니크 인덱스가 걸려 있고, URL·덤프·
   시드 매칭이 전부 이 값으로 돈다. 기존 명명 규칙은 `<두세 글자 접두사>-<소재>-<장면>`
   이다(`rm-`, `tp-`, `rp-`, `sn-`, `ae-`, `ch-`).

2. **`choice`·`order`·`count`면 정답도 넣는다.** 안 넣으면 `seed_verify.sql`의
   불변식 3이 잡는다.

   ```sql
   insert into problem_answers (problem_id, answer)
   select id, '{"kind":"choice","index":0}'::jsonb
     from problems where source_key = '...';
   ```

   `order`는 `cards` 길이와 `sequence`가 맞아야 한다(불변식 4). **`cards`는 섞인
   상태로 저장한다** — 정답 순서로 저장하면 아무것도 안 건드려도 정답이 된다.

3. **화면으로 확인한다.** 빈 단계였다면 홈에 링크가 새로 생긴다.
   `stages.id`를 모르면 조회하라(세션 4 2-1).

4. **덤프를 다시 뽑는다.** `problems.json`은 언제나. **정답을 넣었으면
   `answers.json`도** 함께 뽑는다(세션 4 6-2에 세 쿼리가 다 있다).

5. **`npm run gen:seed` → `npm run test:scoring` → `git add seed seed_data.sql`**

**주의: 이미 문항이 있는 DB에 `seed_data.sql`을 돌려도 갱신되지 않는다.**
문항은 `where not exists (source_key)` 가드라 새 DB 부트스트랩에서만 새 값이
들어간다(세션 4 6-5). 지금은 DB가 항상 최신이라 문제없다.

**문항을 만들 때 반드시 지킬 것** — 세션 3의 2-2다. 모범답안이 통과하는지만
보면 뚫린다. **"지시대로 하지 않은 답안"이 실제로 미달인지 함께 확인하라.**
3단계 초안은 모범답안이 8/8 통과했는데도 절반이 뚫려 있었다.
선택형이면 세션 3의 4-1도 본다 — 정답을 세는 것만으로 맞힐 수 있는 표면 지표

## 8. 사용자와의 작업 방식

세션 3 문서 10장, 세션 4 문서 9장이 그대로 유효하다. 아래는 세션 5에서 새로
확인된 것이다.

### 8-1. 어시스턴트가 세션 5에서 저지른 실수

**(가) 있는 것을 없다고 몰아갔다.** 사용자가 `.env.local`에
`SCORING_SERVER_URL`이 있다고 알렸을 때, `SCORING_SERVER_SECRET`도 있는지
물어봐야 했는데 "URL만으로는 안 붙는다"고 단정했다. 실제로는 둘 다 있었다.
**모르는 것은 묻는다. 없다고 단정하지 않는다.**

**(나) 화면 주소를 잘못 줬다.** "1·2단계 문항 화면을 보라"면서 `/train/1`·
`/train/2`(목록)를 줬다. 목록에는 `instruction`이 안 나오므로 확인이
성립하지 않았다. **무엇을 보라고 할 때 그 화면에 그것이 있는지 확인해라.**

**(다) 셸에 붙여넣을 것과 설명을 섞었다.** `# requirements.txt 의 kiwipiepy 를…`을
명령 블록에 넣어 사용자가 그대로 붙여넣었고 주석으로 먹혀 파일이 안 고쳐졌다.
`git diff --stat`에 파일이 안 보여서야 알았다. **세션 4의 9-1 (다)와 같은
실수다** — 실행할 것과 참고용을 섞지 마라.

**(라) `&`를 빠뜨린 명령을 그대로 물려줬다.** 세션 3 문서 0-4를 검증 없이
인용해 사용자가 두 서버를 한 터미널에 붙여넣었다.

### 8-2. 값이 컸던 패턴

**설계를 세우고 반드시 뚫어본다.** 세션 3의 10-3 그대로다. 세션 5에서 값이
컸던 것도 전부 같은 형태였다 — 6단계 목록을 20건으로 뚫어 12건이 통과하는
것을 보고, 보수안을 만들고, 32건으로 오탐을 재고, 다시 뚫었다.

**빨간불을 먼저 만들어 검사가 무는지 확인한다.** 목록 일치 검사를 DB 갱신 전에
넣어 16건 실패를 보고, DB를 고쳐 16건 통과로 뒤집히는 것을 봤다. 초록불에서
시작했으면 그 검사가 도는지 알 수 없었다.

**커밋 메시지에 판단의 근거를 남긴다.** 세션 5의 커밋 여섯 개는 전부 "무엇을
고쳤나"가 아니라 "왜 그렇게 정했나"를 담았다. 문서가 사라져도 `git log`에 남는다.

**모범답안을 저장소에 넣지 않는다.** 세션 5에서 오탐 감시 픽스처에 6단계
모범답안 8개를 넣을 뻔했다. 세션 3의 2-5가 금지하는 것이고, 저장소는 세션마다
public으로 열린다. **모범답안이 아닌 문장을 새로 지어 넣었다.**

### 8-3. 지시서 나누기 — 세션 5의 실제 적용

세션 4의 9-3("지시서는 나눠라, 단 같은 파일 안의 일이면 묶어라")을 이렇게 썼다.

```
B1  verify.ts 확대 + 픽스처 + cards 타입     더하기만. 테스트 수가 늘어나는지가 지표
B1.5 목록 일치 검사                          일부러 빨간불
C   SQL (사용자 직접)                        빨간불 → 초록불
D   목록 두 건                              같은 파일이라 묶음
E   hybrid 거짓 신호                        다른 파일이라 분리
B2  selftest.py                            Python이라 분리
```

**지시서마다 검증 신호를 하나씩 박았다.** B1은 테스트 수, C는 SQL 결과 8행,
D는 목록 화면, E는 제출 결과 화면, B2는 로컬·HTTP 두 숫자. 신호가 겹치는
작업만 묶었다.

### 8-4. 확인은 화면으로 받는다 — 세션 5의 증거

`tsc`·`lint`·`test:scoring`이 전부 초록불인데 화면에서 갈린 것이 넷이다.

```

목록에서 통과한 문항이 번호를 잃음      테스트로는 안 보인다
라벨이 두 줄로 넘침                   40자 기준은 3번만 잘랐는데 화면은 5번도 넘쳤다
hybrid 가 거짓 신호를 냄               needsAi 가 응답에 실려 있는데 화면이 안 씀
```

**지시서마다 어떤 주소를 열어 무엇을 보면 갈리는지 적어라.**
