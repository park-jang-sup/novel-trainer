# 인수인계 — 세션 4

`인수인계_세션3.md`의 **후속**이다. 세션 3 문서를 지우지 마라 — 이 문서는
세션 4에서 바뀐 것과 새로 확인한 것만 담는다. 문항 자산(6장), 작법 문서
융합 방침(7장), Kiwi 태깅 사실(5-1)은 세션 3 문서에 그대로 살아 있다.

**세션 3 문서에서 틀린 것은 이 문서 2장에 정정해 두었다. 두 문서가
어긋나면 이 문서를 따른다.**

작업일: 2026-08-22

---

## 0. 작업 환경 — 세션 3에서 바뀐 것

세션 3 문서 0장(Kiwi 설치, 저장소 열고 닫기, 로컬 실행)은 **그대로 유효하다.**
아래만 갱신됐다.

### 0-1. 시드 파일이 셋으로 나뉘었다 ★

```
seed_schema.sql   테이블·GRANT·RLS 정책.        손으로 유지. 설계 근거 주석이 여기 산다
seed_data.sql     stages + 문항 + 정답 + 골든셋.  자동 생성. 손으로 고치지 마라
seed_verify.sql   불변식 9건.                    손으로 유지. 마지막에 돌린다
```

실행 순서는 **schema → data → verify**다. 세 파일 맨 위에 주석으로 적혀 있다.

`seed_all.sql`, `seed_convert.sql`, `scripts/gen-convert-seed.ts`는 삭제됐다.
세션 3 문서가 `seed_all.sql`을 언급하는 부분은 전부 위 셋으로 읽어라.

### 0-2. 문항의 단일 출처는 DB 덤프다 ★

```
seed/dump/stages.json     단계 25
seed/dump/problems.json   문항 53
seed/dump/answers.json    정답 13 + 골든셋 7
```

**이 JSON을 손으로 고치지 마라.** DB에서 고치고 다시 덤프한다. 6장에 절차가 있다.

### 0-3. Supabase SQL Editor의 경고 처리

- `select format(...)`처럼 SQL 문자열을 **생성만** 하는 쿼리에도
  "Potential issue detected / Run and enable RLS"가 뜬다. 정적 검사의 오작동이다.
  **"Run and enable RLS"를 절대 누르지 마라.** `problems`에 Supabase가 제 나름의
  정책을 얹어 5-3의 권한 설계와 충돌한다. Cancel하고 쿼리를 바꿔라.
- 해결책: SQL을 만들지 말고 **JSON으로 뽑아라**(`jsonb_agg` + `jsonb_pretty`).
  검사에 걸릴 문자열이 없다.
- `seed_schema.sql`에는 `drop policy if exists`가 있어 "destructive operations"
  경고가 뜬다. 이건 정상이고 `Run query`를 누르면 된다.

## 2. 정정 ★

### 2-1. `stages.id`는 1~25가 아니다. `order_no`로 추측하지 마라 ★★

세션 3 문서 3-6은 "`stage_id`는 uuid가 아니라 정수"라고만 적었고,
"`/train/5`는 6단계"를 특수 사례처럼 다뤘다. **일반 규칙이다.**

`adverb_exception`은 나중에 삽입돼 **`stages.id`가 97**이다.
그 뒤 `order_no`만 5로 끼워 넣었으므로 `id`와 `order_no`는 아무 관계가 없다.

```
문장 5 부사를 쓸 자리  →  /train/97
문장 6 감각 묘사       →  /train/5
구성 3 호감 확보       →  /train/13
구성 4 궤도 이탈 찾기  →  /train/14
```

**세션 4의 어시스턴트는 이 숫자를 세 번 추측해서 세 번 다 틀렸다**(25, 4, 그리고
"13은 14단계"). 추측하지 마라. 홈에서 클릭하거나 DB에서 조회하라.

```sql
select id, track, order_no, title from stages order by track, order_no;
```

**코드에서도 마찬가지다.** 링크 주소는 반드시 `stages.id`로 만든다.
`order_no`로 만들면 문장 5단계 이후가 전부 엉뚱한 곳으로 간다.
화면에 내는 번호(트랙 상대 번호)와 주소에 쓰는 값(`stages.id`)은 다르다.

### 2-2. 저장소 미반영은 12문항이 아니라 28문항이었다

세션 3 문서 8장은 "5·6단계 12문항"만 적었다. 실제로는 **3·4단계 16문항도**
저장소에 없었다. 28 = 3단계 8 + 4단계 8 + 5단계 4 + 6단계 8.

`seed_all.sql`에는 25문항(1·2·14·17·19·20단계)만 있었다.

### 2-3. `stages`도 여덟 군데 어긋나 있었다

세션 3의 `+100 → -99` 밀기가 DB에만 반영됐다. `seed_all.sql`의 단계 정의에는
`adverb_exception`이 없었고, `sensory`부터 `cliffhanger`까지 일곱 단계의
`order_no`가 하나씩 어긋나 있었다.

`on conflict (skill_key) do nothing` 때문에 기존 DB에 돌리면 조용했다.
**새 DB로 부트스트랩했다면 `adverb_exception` 4문항이 `stage_id` null로 들어가
화면에서 사라졌을 것이다.**

지금은 `do update`로 바뀌었다. 6장 참조.

### 2-4. 단계 총수는 24가 아니라 25, 빈 단계는 14가 아니라 15

세션 3 문서 1장의 수치는 `adverb_exception` 신설 직후 갱신되지 않았다.

### 2-5. 불변식 2가 `forbidLemmas`를 몰랐다

세션 3이 `forbidLemmas`를 도입하면서 불변식을 같이 넓히지 않았다.
`sn-kongjwi-night`("깨진 독이 검게 보였다…")는 `forbidWords` 13개 중 어느 것에도
안 걸리고 `forbidLemmas`의 `보`·`어둡`·`검`에만 걸린다.

**그대로 뒀으면 시드 전체가 롤백됐다.** 지금은 "`forbidWords` 또는 `forbidLemmas`
중 하나에는 걸린다"로 넓혔다.

### 2-6. `is_active` 가드가 코드와 정책에서 달랐다

```
RLS 정책          is_active is not false   (null 도 활성)
train page 쿼리   .eq('is_active', true)   (null 이면 제외)
```

`is_active`가 null인 행은 정책은 통과하고 화면 쿼리에서만 빠졌다.
지금은 코드가 `.not('is_active', 'is', false)`로 통일됐다. **새 쿼리를 쓸 때도
정책과 같은 가드를 써라.**

### 2-7. `seed_convert.sql`은 실행할 수 없는 파일이었다

`npm run gen:seed > seed_convert.sql`이 npm 자체 배너까지 파일에 담아
1~4행이 SQL이 아니었다. 지금은 파일이 삭제됐고, 새 스크립트는
`writeFileSync`로 직접 쓴다. **생성 스크립트를 만들 때 리다이렉트를 쓰지 마라.**

### 3-1. 입구를 만들었다

세션 시작 시점에는 `app/page.tsx`가 create-next-app 기본 템플릿이었고,
`app/train/[stageId]/page.tsx`가 `limit(1)`로 단계당 문항 하나만 가져왔다.
**53문항 중 실제로 화면에 닿는 것은 10개뿐이었다.** `limit(1)`에 `order by`가
없어 어느 문항이 뜰지 보장되지도 않았다.

지금 구조:

```
/                            트랙 3 · 단계 25 · 진도 "3 / 8"
/train/<stages.id>           그 단계의 문항 목록. difficulty, source_key 순
/train/<stages.id>/<key>     문항 하나
```

- 문항 주소는 `source_key`다. 순번이 아니다 — 4장 참조
- `stageId`가 문항의 실제 `stage_id`와 다르면 404가 아니라 **정식 주소로 리다이렉트**
- 없는 `source_key`는 404
- 문항 0개 단계는 링크를 만들지 않고 "준비 중"으로 표시

### 3-2. 진도 표시가 붙었다

이 저장소가 `submissions`를 **읽는 첫 코드**였다. 그때까지 삽입만 했다.
`passed=true`인 `problem_id`를 Set으로 모아 단계별로 센다.

`user_id` 조건을 코드에 넣지 않고 RLS 정책(`own submissions read`)에 맡겼다.
코드에서 또 거르면 정책이 도는지 안 도는지 구분할 수 없기 때문이다.
**실제로 돌았다** — 화면에 진도가 떴다.

### 3-3. 시드를 재구성했다

6장 전체가 이 내용이다.

## 4. 세션 4의 결정과 근거

### 4-1. 문항 URL은 순번이 아니라 `source_key`다 ★

어시스턴트가 처음에 `/train/<stage>/<1-based 순번>`을 제안했고, 반박을 받아
철회했다. 근거 넷:

1. **순번은 삽입에 안 버틴다.** 7~11단계를 채우다 `difficulty 1` 문항을 하나
   넣으면 그 뒤 순번이 전부 밀린다. 3번을 가리키던 주소가 다른 문항이 된다
2. `source_key`는 바로 이 목적으로 만들어진 컬럼이다. 유니크 인덱스가 있고
   53문항 전부 값이 있다
3. 나중에 `problems.order_no`를 넣어도 URL이 안 변한다. 순번 방식은 정렬 기준을
   바꾸는 순간 주소 전체가 재배치된다
4. 디버깅 왕복이 사라진다. 대화에서 문항을 `sn-gyeonu-bridge`로 부르는데
   주소가 같은 이름이면 "그 문항 열어봐라"가 한 번에 끝난다

**"3 / 8" 진도 표시는 잃지 않는다.** URL은 `source_key`, 화면은 순번이다.

### 4-2. 트랙 상대 번호가 강제다 ★

`order_no`는 트랙마다 구간이 다르다. sentence 1~11, structure 11~20, start 1~4.
**11번이 두 개다.** 전역 번호는 성립하지 않으므로 트랙 안 상대 번호로 낸다.

```
sentence → "문장"   structure → "구성"   start → "도입"
```

`order_no` 11인 `lack`은 화면에 "구성 1"로 나온다.

### 4-3. 목록 라벨은 지문 첫 문장, 없으면 지시문 첫 문장 ★

처음엔 `instruction`을 라벨로 썼는데, 4단계는 8문항 중 6개의 `instruction`이
글자 그대로 같아 목록이 여섯 줄 똑같이 나왔다. 6단계는 반대로 `instruction`이
길어 한 줄이 세 줄을 먹었다.

규칙: `passage` 첫 문장 → 없으면 `instruction` 첫 문장 → 40자에서 자르고 `…`.
우측에 `source_key`를 mono·`--ink-soft`로 붙인다.

**`choices` 첫 항목을 라벨로 쓰는 안은 버렸다** — 5단계 두 문항이 둘 다
정답 `index 0`이라 목록에서 정답이 드러난다.

### 4-4. 잠금은 만들지 않았다

`is_free=false`인 6단계가 전부 문항 0개다. 지금 잠그면 빈 칸에 자물쇠를 다는 것이다.
문항 수만 표시하고, 0개 단계는 링크를 비활성화했다.

### 4-5. 비로그인 홈은 만들지 않았다

홈을 공개하려면 `stages`에 anon GRANT와 정책을 둘 다 손대야 한다.
5-3의 권한 설계를 건드리는 일이고 지금 얻는 게 없다. `proxy.ts`가 로그인으로
보내는 지금 상태로 둔다.

### 4-6. DB가 단일 출처고, 저장소는 생성물을 담는다 ★

세션 2·3이 문항을 DB에서 만들고 저장소에 안 내려 28문항이 갈라졌다.
`stages`도 여덟 군데 갈라졌다. **사람이 SQL을 손으로 쓰는 한 이 격차는 계속 생긴다.**

대가로 `seed_all.sql`의 문항별 주석은 사라졌다. 설계 근거 주석은
`seed_schema.sql`과 `seed_verify.sql`(손으로 유지하는 두 파일)로 옮겼다.

## 5. 확인한 사실 — 다시 재지 말 것

세션 3 문서 5장(Kiwi 태깅, 권한 설계, `publicConfig` 필터 등)은 그대로 유효하다.
아래는 세션 4에서 새로 확인한 것이다.

### 5-1. 불변식 1은 24문항 전부 통과한다

`remove` 유형(rm 8 + tp 8 + rp 8)의 지문이 전부 `maxChars`를 넘는다.
가장 빠듯한 것이 여유 +2다.

```
rp-magpie-bridge   40자 vs 상한 38   +2
rp-siblings-rope   42자 vs 상한 40   +2
rp-rabbit-liver    47자 vs 상한 44   +3
tp-*               +25 ~ +31         (지문이 다섯 문장이라 넉넉하다)
```

**4단계 문항을 손댈 때는 여유가 2자밖에 없다는 걸 기억해라.**

### 5-2. 불변식 2는 `sensory` 8문항 중 7개가 `forbidWords`로 걸린다

`sn-kongjwi-night`만 `forbidLemmas`로 걸린다. 2-5 참조.

### 5-3. `convert-seeds.ts`는 DB와 완전히 일치한다

`emotion_action` 6문항의 `forbidWords`·`maxChars`·`maxAdverbs`가 DB와 같다.
갈라진 데가 없다.

**이 파일을 삭제하지 마라.** 단순 데이터가 아니라 `lib/scoring/verify.ts`(417줄)가
여기에 불변식 둘을 건다:

1. 지문의 감정어가 `forbidWords`에 걸린다
2. **`forbidWords`의 어떤 어간도 흔한 단어의 접두사가 아니다**

2번이 중요하다. `보` 같은 어간을 넣으면 "보리·보물·보내다"가 전부 걸려 좋은
답안을 미달로 만든다. **`sensory`의 `forbidLemmas` 25개는 이 검사를 한 번도
받은 적이 없다.** 7장 1순위가 그것이다.

### 5-4. 채점 경로가 실증됐다

`ch-village-approval`을 제출해 "통과 / 정답 맞음"이 떴다.
`problem_answers`를 `service_role`로 읽는 자리가 돈다 — 5-3의 GRANT 설계가
처음으로 실제 검증됐다. "일부 검사는 문장 분석 서버가 연결되면 표시됩니다"는
정상이다(형태소 서버 미배포, choice는 그것 없이 판정된다).

### 5-5. 재실행 안전성이 확인됐다

기존 데이터가 있는 DB에 `seed_data.sql`을 돌렸는데 문항이 53에서 늘지 않았다.
`where not exists (source_key)` 가드가 작동한다.

시드 실행 뒤 확인 쿼리:

```sql
select
  (select count(*) from stages)                           as stages,   -- 25
  (select count(*) from problems)                         as problems, -- 53
  (select count(*) from problems where stage_id is null)  as orphan,   -- 0
  (select count(*) from problem_answers)                  as answers,  -- 13
  (select count(*) from golden_cases)                     as golden;   -- 7
```

`orphan`이 핵심이다. 0이 아니면 `skill_key`로 stage를 못 찾은 문항이 있다는
뜻이고, 그 문항은 화면에서 조용히 사라진다.

### 5-6. `seed_verify.sql`의 notice는 Supabase 결과창에 안 보인다

"Success. No rows returned"만 뜬다. **오류 없이 끝난 것 자체가 불변식 9건
전부 통과했다는 뜻이다** — 하나라도 깨졌으면 `raise exception`으로 멈춘다.
숫자로 확인하려면 5-5의 쿼리를 따로 돌려라.

## 6. 시드 운영 — 문항을 고치는 절차 ★

**이 장이 세션 4의 핵심 산출물이다.** 이 절차를 지키지 않으면 세션 2·3이 만든
28문항 격차가 다시 생긴다.

### 6-1. 절차

1. **DB에서 고친다.** `update problems ... where source_key = '...'`
2. **화면으로 확인한다.** `npm run dev` 후 해당 단계를 연다
3. **덤프를 다시 뽑는다.** 아래 쿼리를 돌려 `seed/dump/problems.json`에 **덮어쓴다**
4. **재생성한다.** `npm run gen:seed`
5. **함께 커밋한다.** `git add seed seed_data.sql`

### 6-2. 덤프 쿼리

문항:

```sql
select jsonb_pretty(jsonb_agg(t order by t->>'order_no', t->>'difficulty', t->>'source_key'))
from (
  select to_jsonb(x) as t
  from (
    select s.skill_key, s.order_no, p.type, p.scoring_mode,
           p.instruction, p.passage, p.choices, p.scoring_config,
           p.source_tag, p.genre_tag, p.tone_tag, p.difficulty, p.source_key
    from problems p
    join stages s on s.id = p.stage_id
  ) x
) y;
```

단계:

```sql
select jsonb_pretty(jsonb_agg(t order by t->>'track', (t->>'order_no')::int))
from (
  select to_jsonb(x) as t
  from (select track, order_no, title, skill_key, summary, is_free from stages) x
) y;
```

정답·골든셋:

```sql
select jsonb_pretty(jsonb_build_object(
  'answers', (
    select jsonb_agg(jsonb_build_object('source_key', p.source_key, 'answer', a.answer)
                     order by p.source_key)
    from problem_answers a join problems p on p.id = a.problem_id
  ),
  'golden', (
    select jsonb_agg(jsonb_build_object(
             'source_key', p.source_key, 'content', g.content,
             'expected', g.expected, 'note', g.note) order by p.source_key, g.content)
    from golden_cases g join problems p on p.id = g.problem_id
  )
));
```

### 6-3. 파일 저장은 IntelliJ로 해라

JSON이 5만 바이트 가까이 되어 터미널 붙여넣기는 잘리거나 깨질 수 있다.
IntelliJ에서 파일을 만들고 붙여넣은 뒤 Ctrl+S로 저장한다.
BOM이 붙을 수 있으니 확인은 `encoding='utf-8-sig'`로 한다.

```bash
python3 -c "import json;print(len(json.load(open('seed/dump/problems.json',encoding='utf-8-sig'))))"
```

**주의: 폴더를 만들 때 우클릭 대상이 저장소 루트인지 확인해라.**
세션 4에서 `scoring-server` 안에 만들어 한 번 옮겼다.

### 6-4. `git add seed`만 하면 생성물이 빠진다 ★

`seed_data.sql`은 `seed/` 안이 아니라 **저장소 루트에 있다.**
세션 4에서 두 커밋이 이 때문에 생성물 없이 올라갔고 뒤늦게 맞췄다.

```bash
git add seed seed_data.sql     # 또는 git add -A
```

`git diff --stat`으로 **두 파일이 함께 움직이는지** 확인하는 게 지표다.

### 6-5. 문항 갱신의 비대칭 — 알려진 한계

```
stages   on conflict (skill_key) do update    → 기존 행이 갱신된다
문항     where not exists (source_key)         → 기존 행이 갱신되지 않는다
```

**이미 문항이 있는 DB에 `seed_data.sql`을 돌려도 지문 수정이 반영되지 않는다.**
새 DB 부트스트랩에서만 새 값이 들어간다. 지금은 DB가 항상 최신이라(DB에서 먼저
고치므로) 문제가 없지만, 다른 환경에 반영할 때 알고 있어야 한다.
7장 4순위가 이것이다.

### 6-6. `stages`의 2단계 갱신

`order_no`에 유니크 제약이 걸려 있어 `do update`가 중간 상태에서 충돌할 수 있다.
생성 스크립트는 먼저 대상 행의 `order_no`에 1000을 더해 비켜 두고, 그다음
최종값으로 내린다. 세션 3의 `+100 → -99`와 같은 이유다.

## 7. 다음에 할 일 (권장 순서)

### 1순위 — `verify.ts`를 53문항으로 넓힌다

지금은 `convert-seeds.ts`의 6문항만 검사한다. `sensory` 8문항이 공유하는
`forbidLemmas` 25개는 "어떤 어간도 흔한 단어의 접두사가 아니다" 검사를 받은 적이 없다.

`seed/dump/problems.json`을 읽어 53문항 전부에 불변식을 걸도록 바꾼다.
`convert-seeds.ts`는 그 시점에 역할이 끝나므로 정리 대상이 된다
(`reviewedCollisions` 개념과 주석은 살려서 옮겨라).

**표제어 형식(`보/VV`)과 어간 형식(`두려`)은 판정 방식이 다르다.**
세션 3 문서 4-2에 그 구분이 적혀 있다. 같은 검사를 그대로 적용하면 안 된다.

### 2순위 — `check:seed`

덤프와 생성물이 갈라지는 것을 막는다. `npm run gen:seed`를 돌린 뒤
`git diff --exit-code seed_data.sql`이 깨끗한지 본다. 6-4에서 실제로 겪은 사고다.

### 3순위 — 7~11단계 문항 채우기

세션 3 문서 8장 2순위 그대로다. 이제 **덤프 → 생성 → 검증** 경로가 서 있으니
DB에서 만들고 6장 절차를 밟으면 저장소에 자동으로 남는다.

세션 3 문서 7-2·7-3에 어떤 원칙이 자동 판정 가능한지 정리돼 있다.

### 4순위 — 문항 갱신의 비대칭 해소

6-5 참조. `source_key` 기준 `on conflict do update`로 바꿀지,
아니면 지금의 "새 DB에서만 반영" 동작을 명시적 설계로 남길지 정한다.

### 5순위 — 선택지에 번호를 붙일지

`choice` 유형 화면에 선택지 번호가 없다. "세 번째가 왜 틀렸나"를 물을 수단이
없고, 대화에서 선택지를 가리키기도 불편하다. `order` 유형은 이미 순서 번호를
매기므로 일관성 측면에서도 볼 만하다.

**주의: DB의 `answer.index`는 0부터다.** 화면에 1부터 매기려면 변환이 필요하고,
그 변환을 어디에 둘지가 결정 사항이다.

## 8. 알려진 결함 · 미확인

### 8-1. 형태소 서버가 아직 없다

`SCORING_SERVER_URL`이 없으면 `analyze()`가 null을 돌려주고 형태소 기반 검사는
`pending`으로 남는다. `remove`·`convert` 유형(38문항)이 여기 걸린다.
choice·order·coinage·count 15문항만 완전 판정된다.

### 8-2. `submissions`에 과거 제출이 남아 있다

세션 2·3에서 채점을 시험하며 남긴 `passed=true` 행이 있다.
진도 표시에 그대로 반영된다(문장 1: 1/8, 구성 7: 1/3, 구성 10: 1/2 등).
채점 규칙을 고쳐도 과거 통과 기록은 남는다는 뜻이다. 지금 손댈 일은 아니다.

### 8-3. 목록 정렬은 `difficulty, source_key`다

`problems`에 순서 컬럼이 없어서다. `difficulty`가 1~3이라 같은 난이도 안에서는
`source_key` 알파벳순이 된다. 의도한 학습 순서와 다를 수 있다.
`problems.order_no`를 도입한다면 URL은 `source_key`라 안 깨진다(4-1).

## 9. 사용자와의 작업 방식

세션 3 문서 10장이 그대로 유효하다. 아래는 세션 4에서 추가로 확인된 것이다.

### 9-1. 어시스턴트가 세션 4에서 저지른 실수 — 반복하지 마라

**(가) 숫자를 추측했다.** `stages.id`를 세 번 지어내 세 번 다 틀렸다.
"나중에 삽입됐으니 25일 것"처럼 근거 없는 추론을 사실처럼 말했다.
**모르면 조회하라고 말해라.** 이 프로젝트의 작업 방식은 "재보고 말한다"다.

**(나) 확인 없이 회귀라고 단정했다.** 스크린샷에서 본문이 오른쪽에 치우쳐
보이는 것을 "이번 작업이 만든 레이아웃 회귀"라고 했는데, 사용자가 캡처를
잘라낸 것이었다. 같은 스크린샷의 북마크바가 왼쪽에서 잘려 있는 게 이미 근거였다.
**화면 문제를 지적하기 전에 그림 자체의 조건을 먼저 봐라.**

**(다) 실행할 SQL과 참고용 SQL을 구분하지 않았다.**
`and not exists (...)`로 시작하는 조각을 주면서 "파일 안에서 갈아끼울 자리"라고
적지 않아 사용자가 그대로 실행해 문법 오류를 봤다.
**실행할 것인지 붙여넣을 조각인지 명시해라.**

**(라) `git add` 경로를 잘못 줬다.** `seed_data.sql`이 루트에 있는데
`git add seed`만 안내해 두 커밋에서 생성물이 빠졌다.

### 9-2. 지시서 작성

Claude Code용 지시서에는 **반드시** 다음을 넣어라.

- `AGENTS.md`를 먼저 읽으라는 지시. Next.js 16.3.1 / React 19.2.8이고
  `node_modules/next/dist/docs/`를 읽어야 한다. `app/layout.tsx`가
  `LayoutProps<"/">` 전역 타입을 쓴다
- 하지 말 것 목록. DB 명령 금지, `npm run dev` 금지, 건드리지 말 파일 목록
- `is_active` 가드는 `.not('is_active', 'is', false)`
- 링크는 `stages.id`, 화면 번호는 트랙 상대 번호
- 새 색 도입 금지, 이모지·아이콘 금지(활자 기호 `○ · ×`를 쓴다)
- 마친 뒤 `npx tsc --noEmit`, `npm run lint`, `npm run test:scoring`

### 9-3. 지시서는 나눠라

세션 4에서 라우팅과 홈을 나눠 얻은 것: `/train/13`이 14단계가 아니라는 것을
한 화면에서 바로 짚었다. 둘을 묶었으면 라우팅·RLS·레이아웃 중 어디가 깨졌는지
가리기 어려웠을 것이다.

**단, 같은 파일 안의 일이면 묶어라.** 목록 라벨 수정처럼 한 파일을 두 번
고칠 일은 나누는 이득이 없다.

### 9-4. 확인은 화면으로 받아라

`tsc`·`lint` 통과는 "코드가 돈다"의 증거가 아니다. 세션 4에서 실제로 갈린 것은
전부 스크린샷이었다. 지시서마다 **어떤 주소를 열어 무엇을 보면 갈리는지**를
같이 적어라.
