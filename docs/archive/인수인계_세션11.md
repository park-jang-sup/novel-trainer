## 2. 값을 박은 감시와 사실만 재는 감시 ★

같은 세션에서 둘이 나란히 시험받았다.

```
E'' 감시   eLiterals === 32          값을 박았다 → 문항이 느는 첫 순간에 죽었다
겹침 감시   좋은답안최대 >= 베끼기최소   사실만 잰다 → 지문 둘을 갈아도 안 죽었다
```

세션 10이 `실측 32` 를 감시에 박았다. 10단계 8문항이 들어오며 48이 됐고, 등식은
성립하는데(`48 === 48`) `=== 32` 에 걸려 죽었다. **등식만 남기고 절대 수는 주석으로
내렸다.** `=== 48` 을 새로 박지 마라 — 다음 단계에서 또 걸린다.

겹침 감시는 반대로 짰다. 값(7~9)을 안 박고 `겹치는가` 만 잰다. 지문 둘을 갈아
베끼기 최소가 바뀔 수 있었는데 안 죽었다. **값을 박았으면 죽었을 것이고, 그러면
다음 사람이 겹침을 다시 재는 대신 감시를 맞추려고 지문을 되돌렸을 것이다.**

```
감시에 값을 박으면 그 값이 바뀌는 날 감시가 대상을 되돌리게 만든다
사실만 재라. 값은 주석에 남겨라
```

`seed_check.sql` 도 같은 종류다. 세션 10 §2 의 `안 바뀌는 것이 검산이다` 를 좁혀라.

```
md5 는 덤프 문자열에서 뽑는다. SQL 표기만 바꾸면 안 바뀐다   ← 세션 10 이 잰 것
덤프 내용이 바뀌면 바뀐다. 문항이 늘면 바뀌는 것이 정상이다
```

## 3. 병2 정정 — `아직` 이 아니라 `설 자리가 없다` ★

`validateActionItem` 의 지문 꼴 정규식은 안 문다. `passageOf(item)` 이 만든 것을
`passageOf` 의 조건으로 재기 때문이다 — 자기가 만든 것을 자기가 검사한다.

세션 11이 **"덤프 대조가 붙는 날 처음 일한다"고 적었다. 틀렸다.** 덤프 대조를
세우고 덤프 `passage` 에서 `[복선]` 표기를 빼서 재봤다.

```
덤프 ↔ 픽스처 일치   fail   ← 이것이 잡았다
꼴 정규식            통과   ← 여전히 안 문다
```

**덤프 대조는 동등을 잰다. 그것이 꼴보다 세다.** 문자열이 글자 하나까지 같은지
보는 것이 꼴이 맞는지 보는 것보다 강하다. 동등 검사가 있는 자리에서 꼴 검사는
원리적으로 잉여다.

```
지우지 마라. 그러나 물릴 방법을 찾지도 마라. 다음 사람이 또 재게 된다
물릴 수 있는 자리는 validateActionItem 이 외부 문자열을 인자로 받게 될 때뿐이다
```

## 6. 일의 나눔은 권한으로 갈린다

```
Claude(대화)   근거를 재고 값을 정하고 지시서·SQL 을 만든다. 저장소를 읽는다
Claude Code    저장소 코드를 고친다. DB 자격증명이 없고 브라우저도 없다
사람           SQL 을 Supabase 에서 직접 돌린다. 화면을 보고 답안을 쓴다
```

**'클로드 코드'는 역할 이름이지 도구 이름이 아니다.** 이 세션의 마지막 두 커밋은
사람이 터미널에서 같은 명령을 쳤고 결과가 같았다. 갈리는 것은 권한이다 — DB
자격증명은 사람에게만 있다.

다만 잃는 것이 있다. 클로드 코드가 하면 병 시험을 스스로 재현해 보고한다.
터미널로 하면 그 확인이 빠진다. 그때는 **푸시 뒤 블롭 대조**가 유일한 확인이다.
이 세션은 네 커밋 모두 그렇게 확인했고 네 번 다 일치했다.

### 8-1. 조회로 알아낸 것 — 세션 6 §12 는 다섯 세션째 살아 있다 ★

`가·나·다` 를 재봤다. **`다` 는 이미 서 있고, `가` 는 하나가 아니라 둘이다.**

#### 다 — AI 는 마지막 관문이다. 수로 확인했다

10단계 표본 244건을 `hybrid` 로 두고 `combine` 을 돌렸다.

```
좋은 답안 144건        144 전부 AI 로 간다      ← 오탐 측정 표본
known 뚫기 28건        28 전부 AI 로 간다      ← 미검출 측정 표본 (24 + 전용 4)
잡히는 뚫기 72건        0 건                    ★ 하나도 안 넘어간다
blocked                72 / 96                게이팅이 정확히 그 72를 막았다
────────────────────────────────────────────
AI 에 갈 것             172건   표본 총계 244
```

★ 이 표가 처음에 `27 · 171 · 288` 로 적혀 있었다. 셋 다 틀렸고 원인이 둘이다.

```
27   at-left-draw 에 전용 뚫기가 없었다. 난이도 2가 넷인데 셋만 있었다
     verify 가 if (ex) 로 건너뛰어 아무도 몰랐다 — 세션 10 §4 그 자리다
     ★ 고쳤다. validateActionItem 이 난이도와 전용 뚫기 유무를 대응시킨다
288  bypasses 를 goods 와 같은 144 로 잡았다. 실제는 96 이다
     같은 절이 blocked 72/96 을 정확히 쓰면서 그 옆에서 288 을 썼다
```

**이 수는 오탐·미검출의 분모다.** 분모가 틀리면 `오탐 0/144` 가 무엇의 0인지 모른다.

그리고 규칙 기준선도 `3/11` 이 아니라 **`3/12`** 다. `지문 표기를 베낌` 이
나중에 붙어 분모가 늘었는데 잡히는 쪽이라 미검출 3이 안 변했고, 그래서 아무도
안 걸렸다. 난이도 2는 전용까지 `4/13` 이다.

세션 6이 원칙으로 적은 것이 코드에서 그대로 돈다. 읽어서 안 게 아니라 쟀다.

**세션 6의 `골든셋 7개가 씨앗이다` 가 172건이 됐다.** 갈래가 붙어 있어서
AI 가 무엇을 못 잡는지가 바로 나온다 — 규칙 때 `3/12` 가 한 일과 같은 자리다.

#### 가 — 하나가 아니라 둘이고 크기가 다르다 ★

```
가-1  킬스위치 · 사용자 한도   배선이 다 있다. route.ts TODO 둘을 채우면 된다
가-2  지출 상한               ★ 정정 — 신설이 아니라 배선이다
```

**`ai_usage_log` 테이블이 이미 DB 에 있다.** `seed_schema.sql:64` 에 `grant` 만
있고 `create table` 이 없어서 '새로 만들어야 한다'고 적었는데, 조회해 보니 있다.

```
id · user_id · submission_id · model · input_tokens · cached_tokens
output_tokens · cost_usd(numeric) · created_at
```

`cost_usd` 가 컬럼으로 있다. **비용을 예측할 필요가 없다 — 쟀다가 막으면 된다.**

```

          >= system_flags.daily_spend_cap_usd 면 차단
호출 후   실제 usage 를 insert
```

그리고 이것이 `p_limit` 사슬을 끊는다.

```
p_limit(사용자별 호출 수)과 지출 상한은 서로 다른 두 개의 마개다
지출 상한은 프롬프트가 서기 전에도 켤 수 있다
p_limit 은 여전히 못 정한다 — 그 사슬은 아래 그대로 유효하다
```

`cached_tokens` 가 있는 것은 Gemini 캐싱을 상정한 설계로 보인다. 지문 8건이
반복되니 걸리는 자리다. **왜 그렇게 설계했는지는 안 쟀다.**

안 갈라 두면 다음 사람이 `가` 를 TODO 둘 채우기로 알고 시작한다.

```
system_flags.kill_switch          false    route.ts 주석이 가리킨다. 코드는 안 읽는다
system_flags.daily_spend_cap_usd  20       ★ 코드에도 문서에도 없다. 이번에 처음 봤다
consume_ai_quota(p_user,p_limit)  사용자별 · 하루 · 호출 수 1건씩. p_limit 미정
ai_quota(user_id,date,used,bonus) 상한은 호출자가 넘긴다. DB 에 안 박혀 있다
```

#### `20` 은 한도가 아니다 — 적혀 있을 뿐이다 ★

`daily_spend_cap_usd = 20` 을 읽는 코드가 **하나도 없다.** `consume_ai_quota` 는
호출 수를 세지 달러를 안 세고, 토큰 사용량을 쌓는 테이블이 없다.

```
적혀 있는 것과 걸리는 것은 다르다
```

이 세션이 같은 모양을 세 번 만났다. 계보로 적어 둔다.

```
감시가 0을 낸다      물 표본이 없어서인가, 물 조건이 안 와서인가 (4장)
검사가 통과한다      문다는 증거가 아니다. 병을 넣어 물려야 안다
상한이 적혀 있다     ★ 강제하는 것이 없으면 한도가 아니다
```

다음 사람이 `20` 을 보고 "한도가 있다"고 읽지 않게 하는 것이 이 절의 목적이다.

#### `p_limit` 을 못 정하는 이유의 사슬

```
p_limit 을 정하려면    호출 1회 비용 × 예상 사용자 수 <= 20 USD/일
호출 1회 비용을 알려면  모델과 프롬프트 길이가 필요하다
프롬프트를 짜려면      known 넷을 어떻게 물을지가 필요하다   ← 다음 세션의 첫 자리
```

이 세션은 여기가 경계였다. **잴 수 있는 것은 다 쟀고, 남은 것은 전부 정하는 일이다.**

#### 하니스 경로 — 아직 안 정했다

`consume_ai_quota` 는 `p_user uuid` 를 받는데 회귀 검증에는 사용자가 없다.

```
A  검증용 계정 하나를 만든다     하루 한도가 검증 한 번에 다 나간다
B  옆으로 돈다                 킬스위치가 안 걸린다 ← 세션 6이 막으려던 것
C  옆으로 돌되 자기 상한을 갖는다  취지가 산다 — 킬스위치는 user_id 가 필요 없다
```

C 로 기울지만 **안 정했다.** `가-2` 가 서야 상한의 단위가 정해진다.

#### 흔들림 측정은 회수부터 재라

`같은 답안에 같은 판정이 나오는가`(세션 6 나)를 재려면 몇 회 돌릴지가 필요한데,
**`3회` 는 근거 없는 수다.** 172건을 3회 돌리면 516 호출이고, 그 전에 이렇게 재라.

```
10건쯤을 5회 돌려 흔들림이 있는지부터 본다     50 호출
흔들림이 없으면 1회로 족하다 — 516이 172로 준다
temperature 를 0 으로 두면 달라지는지도 함께 본다
표본은 좋은 답안과 known 을 섞고, known 은 갈래마다 하나씩 넣어라
  좋은 답안만 뽑으면 fail 쪽 흔들림을 못 본다
```

### 9-0. 검사가 통과한 채로 비는 자리 — 계보 셋 ★★

이 셋은 **`test:scoring` 이 통과해도 안 보인다.** `git status` 로만 보였다.

```

```

셋째를 검사로 내렸다 — `docs ↔ README` 를 **두 방향으로** 잰다(`1605 → 1607`).

```
README → 파일    가리키는데 없다
파일 → README    있는데 안 가리킨다   ★ 정규식이 덜 잡는 것을 이쪽이 잡는다
```

한 방향만 재면 안 되는 이유가 실제로 났다. 셸 한 줄
(`grep -oE '[가-힣...]'`)이 한 환경에서는 `Invalid collation character` 로 죽고
다른 환경에서는 **일부만 뽑혔다.** 뽑힌 것이 다 실재하니 `전부 실재` 로 읽혔다.

```
깨진다      바로 안다
덜 잡는다   ★ 통과한 것처럼 보인다
```

첫째·둘째는 아직 검사가 없다. **적어 두는 것과 걸리게 하는 것은 다르다**(8-1장의
`daily_spend_cap_usd 20`). 다음 사람이 이 셋 중 하나를 더 내리면 그만큼 준다.
