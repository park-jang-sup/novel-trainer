## 1. 세션 12의 1순위가 반쯤 틀렸다 ★★

세션 12 §7 이 이렇게 적었다.

```
1순위  A(gate) + B(호출) 를 같은 날 붙인다
       B  route.ts 가 gate 를 부르고 Gemini 를 부른다
```

**`route.ts` 가 첫 호출자라는 전제가 틀렸다.**

```
2순위가 요구하는 것   172건 1회 · 10건 5회 · 경계 36건
그건 route 를 안 탄다  ★ 하니스가 탄다. 그리고 172 는 프로덕션보다 많다
```

그러니 세션 6 §12 의 `안 켜고 붙이면 무제한 호출이다` 는 라우트가 아니라
**하니스에 걸린다.** 마개를 붙일 자리가 거기다.

그리고 지금 `route.ts` 를 배선하면 **실사용에서 한 번도 안 도는 경로**가 선다.

```
needsAi 가 참인 것    2단계 emotion_action 6건뿐
프롬프트 v1 이 재는 것  10단계 action_turn 전용 (4줄 · [결정타] · element)
10단계 8문항          전부 auto. 세션 11 §8 이 `미리 hybrid 로 박아 두기` 를 막았다
────────────────────────────────────────────────────────────
그래서 skill_key 가드를 걸면 **그 가드는 항상 거짓**이다
```

★ 그게 `@anthropic-ai/sdk` 와 같은 꼴이다. 세션 12 §6 이 막으려던 것을
막는 방식으로 저지르게 된다. **`route.ts` 는 10단계가 `hybrid` 로 갈 때 붙인다** —
세션 11 §8 이 정한 순서상 측정이 끝난 뒤다. 그때 붙이면 가드가 실제로 도는
상태에서 선다.

그래서 이 세션의 일은 `A + B(route)` 가 아니라 **`A + 하니스`** 다.
`A` 는 뜨지 않는다 — 하니스가 부른다.

## 2. 하니스 경로를 C 로 닫았다 — 세션 11 §8-1 의 미결 ★

```
A  검증용 계정 하나        하루 한도가 검증 한 번에 다 나간다
B  옆으로 돈다             ★ 킬스위치가 안 걸린다 — 세션 6이 막으려던 것
C  옆으로 돌되 자기 상한    킬스위치도 지출 상한도 user_id 가 필요 없다   ← 이것
```

★ **하니스가 게이트를 안 타면 그게 `B` 다.** 그것이 C 를 고른 이유의 전부다.

두 경로가 마개 셋을 공유하고 넷째만 다르다.

```
라우트   api_key → kill_switch → spend_cap → quota      사용자별 하루 호출 수
하니스   api_key → kill_switch → spend_cap → run_cap    이 실행의 호출 수
```

`가-2`(지출 상한)가 서면서 세션 11 §8-1 의 걱정 하나가 약해졌다 —
`A` 의 `한도가 한 번에 다 나간다` 는 이제 사용자 한도가 아니라 지출 상한이
받는다. 그래도 C 다. **A 는 킬스위치를 사용자 계정에 매다는데, 킬스위치는
user_id 가 필요 없는 마개다.**

`remote.ts`(네트워크)와 `morph.ts`(판정)를 가른 것과 같은 갈래다.

### 3-1. 게이트가 함수 셋인 이유

`consume_ai_quota` 는 **부작용**이다. 킬스위치가 닫힌 채로 차감하면
일어나지도 않은 호출에 사용자 하루치가 깎인다. 그래서 차감 앞의 셋을 먼저
재고 차감은 그 뒤에 잰다.

### 3-2. ★ 못 읽은 값은 전부 차단이다

```
kill_switch 가 null       막는다   못 읽은 채로 통과시키면 마개가 없는 것과 같다
daily_spend_cap 이 null   막는다   상한이 없는 것과 무한인 것을 안 가른다
오늘 지출이 null           막는다   얼마 썼는지 모르면서 상한을 지킬 수 없다
모르는 모델의 비용          null    ★ 0 이 아니다
```

마지막이 중요하다. `costUsd` 가 모르는 모델에 `0` 을 내면 **모델 이름 하나
바뀐 것만으로 지출 상한이 통째로 새고 아무도 모른다.** 세션 11 §8-1 의
`적혀 있는 것과 걸리는 것은 다르다` 가 그 자리다.

## 4. 조회로 알아낸 것 둘 ★★

### 4-1. `system_flags` 는 단일 행이 아니라 key/value 다

```
key                   value
daily_spend_cap_usd   20
kill_switch           false
```

세션 11 §8-1 이 `system_flags.kill_switch` 로 적어서 컬럼처럼 읽혔고,
이 세션도 처음에 단일 행으로 짰다. **그대로 커밋했으면 조회가 늘 0행을 내서
마개가 항상 deny 였다.** 그건 안전하게 죽는 것이 아니라 아무도 못 쓰는 것이다.

★ 계보에 얹는다 — `문서의 표기와 테이블의 모양은 다르다`.
  **모양을 모르는 채로 `가정`을 남기고 커밋하지 마라.** 조회 한 번이면 갈린다.

### 4-2. `ai_usage_log` 에 `select` 이 없었다 ★

```
seed_schema.sql:58  service_role 은 RLS 는 우회하지만 GRANT 는 우회하지 않는다
seed_schema.sql:64  grant insert on public.ai_usage_log to service_role;
                    ★ select 이 없다
```

**스키마 파일이 자기 주석에 그 함정을 적어 놓고 그 아래 줄에서 걸렸다.**
지출 상한은 오늘 `sum(cost_usd)` 를 읽는다 — 첫 호출에서 42501 로 죽는다.
`grant select, insert` 로 고쳤다.

★ 이것이 세션 11 §8-1 의 **세 번째 얼굴**이다.

```
적혀 있는 것과 걸리는 것은 다르다     daily_spend_cap_usd 20 을 읽는 코드가 없었다
★ 있는 것과 읽을 수 있는 것은 다르다   테이블은 있었고 select 이 없었다
```

세션 12가 `ai_usage_log 가 이미 있다` 로 `가-2` 를 신설에서 배선으로 낮췄는데,
**배선에도 이 줄이 필요했다.**

### 4-3. 같은 조회가 `created_at` 도 보여줬다 ★

```
column        is_nullable
user_id       YES    ← 하니스의 null 이 죽지 않는다. 23502 를 기다릴 필요가 없었다
cost_usd      YES
created_at    YES    ★ 이쪽이 문제다
```

`created_at` 이 null 인 행은 `gte` 필터에 **안 걸려 합계에서 조용히 빠진다.**
덜 센 합계로 재는 상한은 상한이 아니다. 그래서 null 인 행을 **오늘로 친다** —
더 세는 쪽으로 틀리면 마개가 일찍 닫힐 뿐이고, 덜 세는 쪽으로 틀리면 마개가
없어진다.

`cost_usd` 도 nullable 이다. 숫자로 못 읽는 행이 하나라도 있으면 합계 대신
`null` 을 낸다 — 그러면 게이트가 `오늘 지출을 못 읽었다` 로 막는다.
값을 못 매긴 호출에 돈이 나갔다는 뜻이니 멈추는 것이 맞다.
★ `costUsd` 가 모르는 모델에 `null` 을 내는 것과 이어진 사슬이다.

### 4-4. 쓰기 예비 검사 — 돈이 나가기 전에 실패한다 ★

```
지금까지   부르고 → insert 실패 → 멈춘다     ★ 첫 호출은 이미 나갔다
고침       표시 행 하나를 먼저 넣어 본다      호출 전에 갈린다
```

`preflightWrite` 가 `cost_usd = 0` 짜리 표시 행(`model='preflight'`)을 넣고
오늘 행 수가 하나 느는지 본다.

★ **이 검사가 실제로 재는 것은 `created_at` 기본값이다.** 넣었는데 오늘로
안 세어지면 진짜 호출의 비용도 합계에서 빠진다는 뜻이다. 나머지 셋 —
select 권한 · insert 권한 · `user_id` 의 not null — 은 그 부산물로 함께
갈린다. **순서를 뒤집어 읽지 마라.** 권한 셋만 보려던 검사였으면 행 수를
셀 이유가 없다.

service_role 에 delete 권한이 없어 표시 행은 못 지운다. **남긴다** —
지우는 권한을 주는 것보다 못 지우는 $0 행 하나가 낫다.

### 4-5. 하니스가 층 셋이 됐다

```
--dry     DB 도 네트워크도 안 탄다. 표본 · 프롬프트 · 틀 길이
          ★ 자격 없이 도는 것이 이 층의 값어치다. README 상태 확인이 쓴다
--check   마개와 쓰기를 재고 멈춘다. Gemini 는 안 부른다
(없음)     --check 를 통과한 뒤 부른다
```

★ `--dry` 에 DB 검사를 얹으려다 되돌렸다. 얹으면 README 의 상태 확인이
자격 없는 사람에게서 죽는다 — 상태 확인은 자격 없이 돌아야 상태 확인이다.

### 4-8. 테이블 권한과 시퀀스 권한은 다르다 ★★

`select` grant 를 DB 에 넣으니 `count` 는 통과하고 `insert` 가 죽었다.

```
code=42501 message=permission denied for sequence ai_usage_log_id_seq
```

`id` 가 `bigserial` 이라 INSERT 가 시퀀스를 당긴다. **시퀀스는 테이블과 다른
객체라 권한을 따로 받는다.** `grant insert on table` 만으로는 못 넣는다.

```sql
grant usage, select on sequence public.ai_usage_log_id_seq to service_role;
```

★ `seed_schema.sql` 위쪽이 `GRANT 와 RLS 는 다른 층이다` 라고 적어 뒀다.
**층이 둘이 아니라 셋이었다** — 테이블 권한 · 시퀀스 권한 · RLS 정책.
`generated as identity` 였으면 이 줄이 필요 없다. `bigserial` 일 때만이라
눈으로는 안 보이고 **넣어 봐야 걸린다.**

★★ 이게 예비 검사가 값어치를 한 첫 자리다. 이 42501 이 172건을 돌리는
중에 났으면 **첫 호출은 이미 나간 뒤**였다. 돈이 나가기 전에 걸렸다.

### 4-7. `head: true` 가 오류 본문을 삼켰다 ★★

첫 `--check` 가 여기서 죽었는데 **무엇 때문인지가 안 나왔다.**

```
ai_usage_log count failed code=undefined message=
```

`countTodayRows` 가 `head: true` 로 HEAD 요청을 보냈다. HEAD 응답은 본문이
없어서 PostgREST 가 실어 보내는 `{code, message, details, hint}` 가 통째로
사라진다. **권한(42501)인지 필터 문법(400)인지를 못 갈랐다.**

★ `검사가 통과한 채로 비는 자리` 의 사촌이다 — 이쪽은 **오류가 오는데
내용이 없다.** 몸통을 안 받는 최적화가 진단을 통째로 지웠다.

```
고침   head 를 빼고 limit(1) 로 몸통을 최소로 둔다. 받기는 받는다
       count 는 Content-Range 헤더로 오므로 limit 이 세는 수를 안 줄인다
       오류는 code · message · details · hint 를 전부 찍는다
       42501 이면 `grant 는 DB 에 가야 걸린다` 를 함께 찍는다
```

그리고 `or=()` 안의 타임스탬프에서 밀리초를 뗐다. PostgREST 는 그 안에서
값을 점(`.`)으로 가르는데 `...T00:00:00.000Z` 는 점을 하나 더 갖는다.
초 단위여도 하루 경계를 재는 데 손해가 없으니 의심 하나를 지웠다.

### 4-6. 그 층 가르기의 대가 — `.env.local` 을 아무도 안 읽었다 ★★

첫 `--check` 가 `DB 자격이 없다` 로 죽었다. **자격은 있었다.** `.env.local` 에
다 있었고 **읽는 코드가 없었다** — `next dev` 는 그 파일을 알아서 읽지만
`tsx` 로 도는 스크립트는 안 읽는다.

```
--dry 는 물기 시험을 다 통과했다   그리고 --check 첫 줄에서 죽었다
★ --dry 는 env 를 안 탄다        자격 없이 도는 층은 자격 쪽 결함을 원리적으로 못 문다
```

층을 가른 판단 자체는 옳다(4-5장). 다만 **가른 층이 못 무는 자리가 생긴다는
것**을 같이 알아야 한다. `--dry` 가 통과했다고 `--check` 가 설 거라고 읽지 마라.

`scripts/load-env.ts` 가 `@next/env` 의 `loadEnvConfig` 를 부른다. 손으로
파서를 쓰지 않은 이유는 하나다 — `.env` · `.env.local` ·
`.env.development.local` 의 우선순위가 `next dev` 와 갈리면 **화면에서 되던
것이 스크립트에서 안 된다.** `@next/env` 는 `next` 가 이미 쓰는 것이고,
transitive 로 두면 조용히 사라질 수 있어 `package.json` 에 명시로 올렸다.

★ 이 import 는 **스크립트의 맨 앞**이어야 한다. `gemini.ts` 가 로드 시점에
`GEMINI_THINKING_LEVEL` 을 읽는다.

그리고 `--check` 가 이제 무엇이 있고 없는지를 **이름으로** 낸다.

```
env  NEXT_PUBLIC_SUPABASE_URL=있음 · SUPABASE_SERVICE_ROLE_KEY=있음 · GEMINI_API_KEY=없음
```

`자격이 없다` 한 줄로는 `파일이 없다` 와 `읽는 코드가 없다` 를 못 가른다.
실제로 그 둘을 헷갈렸다.

## 5. 단가는 공식 페이지에서 확인했다 — 그리고 설계안 8장이 흔들린다 ★★

설계안 8-2 가 `단가는 2차 출처에서 읽은 것이고 공식 페이지가 아니다. 켤 때
다시 확인하라` 고 적었다. 확인했다. `ai.google.dev/gemini-api/docs/pricing`
(2026-08-30).

```
gemini-3.7-flash   입력 $0.75 · 출력 $3.75 · 캐시 $0.075   ★ 프로모
                   2027-01-01 부터 $1.50 / $7.50 / $0.15  ★ 두 배가 된다
```

**단가는 설계안이 맞았다.** 흔들린 것은 단가가 아니라 출력 토큰 수다.

### 5-1. 출력 단가가 생각 토큰을 포함한다

공식 표의 항목 이름이 `Output price (including thinking tokens)` 다. 그리고
**3.7 Flash 의 기본 thinking 은 `medium`** 이다. 설계안 8-1 은 출력을
`JSON 한 줄 · ~100 토큰` 으로 잡았다 — 생각 토큰을 모르고 잡은 값이다.

`thinkingLevel: 'low'` 로 내렸다. 하지만 **그건 아낀 것이지 잰 것이 아니다** —
thinking level 은 토큰 수를 보장하는 값이 아니라 상대적 지침이다.

```
★ $0.21 은 바닥값이지 측정값이 아니다. 0장 계보 셋째가 또 났다
```

처방은 하나다. **172건을 돌리기 전에 10건만 돌리고 `usageMetadata` 를 읽어라.**
`thoughtsTokenCount` 를 포함한 실제 출력 토큰으로 1회 실비를 내고, 그 수를
설계안 8장에 박아라. 10 호출이면 최악에도 $0.04 다. 안 재고 172 를 돌릴
이유가 없다. `scripts/ai-probe.ts` 가 그 일만 한다.

### 5-2. `temperature 0` 축이 없어졌다 — 출처가 둘이고 세기가 다르다

```

                     ai.google.dev/gemini-api/docs/latest-model

                     docs.cloud.google.com/vertex-ai/.../gemini-3-prompting-guide
                     ★ 세대 전체에 대해 '쓰지 말라고 권한다' 고 적는 쪽
```

**세기를 섞지 마라.** `없어졌다` 로만 적으면 나중에 `있는데?` 로 뒤집힌다.
결론은 하나로 모인다 — 설계안 5장 2번과 세션 11 §8-1 의
`temperature 0 에서도 흔들리는지 함께 본다` 는 **못 한다.**

★ 그리고 이건 설계안을 **약화시키는 게 아니라 강화한다.**

```

후   ★ 흔들림을 죽일 수단이 없다. 10건 5회는 선택이 아니라 필수다
```

빈자리에 **`thinkingLevel`** 이 들어간다. 흔들림 측정의 축은 온도가 아니다.


**0 실패에 종료 코드도 0이다.** 세션 11 9-0장의 `검사가 통과한 채로 비는 자리`

```
패치가 안 붙어도 검사는 같다

```

앞의 넷은 **검사가 통과한 채로 빈다.** 다섯째는 다르다 —
**검사가 통과하는데 커밋이 빈다.**

### 6-1. `Promise.all` 만으로는 반만 막힌다 ★

```
명단에 push 한 것만 기다린다
  ★ push 를 잊은 다음 async 단언은 그대로 샌다
  그리고 그건 수가 안 늘어서 안 보인다 (당시 1649)
```

**명단에 넣는 것이 opt-in 이라 빠뜨려도 조용하다** — `감시를 검사 안에 접으면
수가 안 는다` 와 같은 모양이다. 그래서 둘을 함께 세웠다.

```
tAsync(name, fn)   비동기 단언은 이걸로만 적는다. 명단 등록이 자동이다
sealed             최종 줄을 찍은 뒤 t 가 불리면 죽는다
                   ★ 수를 안 박는다. '늦게 왔다' 는 사실만 잰다
```

★★ **`sealed` 는 완전한 그물이 아니다. 이걸 안 적으면 다음 사람이 `tAsync`
를 건너뛴다.** 잡는 것은 최종 줄보다 **늦게 도착한 것뿐**이고, 같은 틱에
도착한 미아는 그냥 세어진다(그건 해가 없다 — 수에 들어갔다).

쟀다. `push` 를 지운 미아가 마이크로태스크 한 틱 차이로 **먼저** 도착해서
`sealed` 를 그대로 통과했다. 당시 수(`1649`)가 그대로 나왔다. 20ms 를 물려야 잡혔다.

```
tAsync    빠뜨릴 수 없게 한다        ← 근본
sealed    그래도 샌 것을 잡는다      ← 그물. 다만 늦게 온 것만
```

### 6-2. `.catch` 가 없으면 최종 줄이 아예 안 찍힌다

```
병8   명단에 안 넣고 늦게 도착하는 단언     ✗ 최종 줄 뒤에 단언이 왔다 · 종료 1
병9   명단의 단언이 던진다 (.catch 있음)   ✗ 비동기 단언이 던졌다 · 1648/1 · 종료 1
병10  같은 상황에서 .catch 를 뺀다         ★ 최종 줄이 아예 안 찍힌다
```

병10 이 위험하진 않다(종료 코드는 1이다). 다만 `tail -1` 만 보는 절차에서는
오류 줄만 보이고 `최종:` 이 없다. 던진 것도 실패 하나로 세고 최종 줄은 찍는다.

세션 12 §5 의 넷에 더한다.

```
적혀 있는 것과 걸리는 것은 다르다
통과하는 것과 문다는 것은 다르다
예측한 것과 잰 것은 다르다

★ 문서의 표기와 테이블의 모양은 다르다     system_flags 는 key/value 다
★★ 한 번 잰 것과 여러 번 잰 것은 다르다   ← 12장. 설계안 0장 계보의 다섯째다
```

앞의 둘은 **조회 한 번으로 갈렸다.** 문서만 읽고는 못 봤다.

셋째는 다르다. **재긴 쟀는데 한 번 쟀다.** 그리고 그 한 번 위에서 원인을
세 번 지목했다(12-2장). `예측한 것과 잰 것은 다르다` 의 **다음 칸**이다.

### 7-1. 지출 상한은 같은 병을 세 번 앓았다 ★★

얼굴만 다르고 병이 하나다. **셋 다 `마개가 있다` 로 보이고 셋 다 마개가 아니다.**

```
1차  상한이 적혀 있고 읽는 코드가 없다        daily_spend_cap_usd 20     세션 11 §8-1
2차  테이블은 있는데 읽을 권한이 없다          grant insert only          이 세션 4-2
3차  ★ 읽히긴 하는데 일부 행이 조용히 빠진다   created_at null            이 세션 4-3
4차  ★ .env.local 에 있는데 읽는 코드가 없다   next dev 만 읽는다          이 세션 4-6
5차  ★ 테이블 권한은 있는데 시퀀스 권한이 없다  bigserial 이라 그렇다       이 세션 4-8
```

다섯 다 **한 문장이다** — `있다` 와 `걸린다` 는 다르다. 다섯 번 다른 얼굴로
나왔고, 다섯 번 다 문서만 읽고는 못 봤다. 여섯째를 만나거든 이 목록에 얹어라.

3차가 제일 안 보인다 — 조회가 성공하고 수가 나오는데 그 수가 덜 센 값이다.
1·2차는 오류가 나거나 코드가 없어서 찾을 수 있었다. 4차는 1차와 **같은 문장**이다 —
`있는 것` 과 `읽는 코드가 있는 것` 은 다르다. 자리만 DB 에서 파일로 옮겼다.

★ 처방의 방향이 정해져 있는 이유도 여기 있다. **비대칭이다.**

```
더 세면    마개가 일찍 닫힌다
덜 세면    마개가 없어진다
```

그래서 모르는 것은 전부 `더 세는 쪽 · 막는 쪽` 으로 붙였다 —
`created_at` null 을 오늘로 치고, `cost_usd` 를 못 읽으면 합계 대신 null 을
내고, 모르는 모델의 비용을 0 대신 null 로 낸다. 셋이 같은 규칙의 세 얼굴이다.

### 12-3. `delete` 는 왜 사망인가 — D-1/D-2 를 갈랐다

`한 갈래가 서고 둘이 무너지는 것`은 `연산이 죽었다` 와 다른 모양이라,
`낱낱 나열 8/8` 이 다른 성질의 부산물인지를 따로 쟀다.

```
D-1  delete 가 그 갈래를 실제로 재고 있다      → 물음을 바꿀 자리다
D-2  다른 성질이 가르고 delete 는 따라만 간다   → 부산물이고 폐기다
```

```
전체 36건   load0 이 어휘 반복과 값이 같은 건수 24/36    ★ 애매하다
갈래별      낱낱 나열   load0 8/8 · 어휘 반복 8/8       ★★ 완전 일치
           그 밖 28건  어휘 반복 1건인데 load0 은 13건
```

전체 24 가 애매했던 이유가 여기 있다. **겹치는 것은 낱낱 나열 8건에서 전부
나오고, 나머지 28건에서 `delete` 가 혼자 움직이는 자리는 흔들리는 자리와
겹친다.** `D-2` 쪽이다.

★ **상관이지 인과가 아니다.** 어휘 반복이 원인인지, 둘 다 `낱낱 나열` 이라는
성질의 두 그림자인지는 안 쟀다. 그래도 결론은 같다 —
`delete` 가 독자적으로 더하는 것이 없다.

### 12-4. `thinkingLevel high` 를 쟀고, `A`/`B` 갈래가 닫혔다

`low` 에서 값이 안 서니 생각을 더 시키면 나아지는지 물었다. **36건 × 5회.**

```
        파싱         load 고정    1회 실비      출력(생각 포함)
low    36/36        22/36       $0.00078      52 중앙
high  27~32/36      20/30       $0.00731      1,953 중앙   ★ 9.4배
```

★ 처음엔 3회만 보고 두 해석이 갈린다고 적었다.

```
해석 A   high 는 이 물음에 안 맞는다          ← 관측 결론
해석 B   maxOutputTokens 2048 이 좁았다      ← 설정 결론
```

`out=2044` 는 한도에 닿았다는 뜻이라 `B` 를 배제 못 했다.
**5회를 다 보니 닫혔다 —** 잘리지 않고 살아 돌아온 30건만 세도 `load` 가
`20/30` 이다. `low` 의 `22/36` 과 같다. **한도를 열어 파싱을 살려도 `load` 는
안 선다.** 추측이 아니라 잰 값이다.

★★ **값보다 파싱이 먼저 죽는다.** 실패 수가 회차마다 `6·5·6·9·4` 로 다르다 —
**실패조차 흔들린다.** 한 건은 `out=0` 으로 아무것도 안 뱉었다. 모델이 JSON 대신
사고 과정을 뱉고, 한국어로 물었는데 영어로 자문자답한다.

★ `high` 가 나은 자리가 하나 있다. **`cue_copied` 가 `low` 28/36 에서
`high` 30/30 으로 완전히 고정된다.** 172건으로 넘길 때 어느 level 로 갈지는
미결이다 — 파싱 손실 4~9건과 맞바꾸는 문제다.

★ 그리고 `delete[0]` 이 `high` 에서 `6/130` 이다. `low` 의 `1/180` 을
**연산의 원리적 한계로 읽으면 틀린다** — 이 설정의 성질이다.

```
high 를 안 쟀다고 하지 마라 — 5회 쟀다
한도가 좁아서 그렇다고도 하지 마라 — 살아 돌아온 30건이 같은 말을 한다
delete 는 low 에서도 high 에서도 안 선다. 사망이다
```

★ 그리고 이 실험을 `$0.01 도 안 든다` 고 잡았다가 `$1.31` 을 썼다.
비용 추정 하나가 아니라 **실패 모드 자체를 못 본 것**이다 — 설계안 8-5장에

### 12-7. ★★ 패치가 안 건드린 것과 커밋될 것은 다르다

문서 패치의 커밋 메시지에 `코드는 안 건드린다. 문서만이다` 라고 적었다.

`1671` 을 적고 있었다 — 손으로 적은 수가 아니라 **커밋되지 않은 코드 위의
실측**이었다. 사람이 그 어긋남을 잡았다.

★★ **`git status` 로도 안 보인다.** `M` 을 다 보여주지만 **어느 `M` 이 어느
