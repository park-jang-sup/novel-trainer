## 1. 저장소를 고쳐도 화면은 안 바뀐다

`instruction` · `passage` · `scoring_config` 는 **DB가 원본이고 저장소는 사본이다.**

```
seed/dump/*.json     사본
seed_data.sql        사본에서 생성
lib/scoring/fixtures 사본
DB (Supabase)        원본. 화면이 읽는 곳
```

`test:scoring 839 통과` 는 **사본끼리 맞는다**는 말이지 화면이 맞다는 말이 아니다.
이번 세션에 저장소만 고치고 "됐다"고 읽은 일이 **세 번** 있었다.

```
404 일곱      seed_data.sql 을 붙여넣다 잘렸는데 stages 만 들어가서
             단계 제목이 바뀐 것을 보고 "적용됐다"고 읽었다
instr_len 214 클립보드가 개행을 CRLF 로 바꿨는데 839 는 그대로 통과였다
187자 반영    f56bea7 을 커밋·확인하고 화면을 봤는데 옛 문장이 그대로였다
```

**이제 `seed_check.sql` 이 셋을 전부 잡는다(5장).**

### 문항 insert 는 갱신하지 않는다

```sql
insert into problems (...) select ...
where not exists (select 1 from problems p where p.source_key = ...);
```

**insert-if-absent 다.** 이미 있는 행은 `seed_data.sql` 을 몇 번 돌려도 안 바뀐다.
`stages` 만 `on conflict (skill_key) do update` 라 갱신된다.
**기존 문항의 값을 고치려면 `update` 문을 따로 써야 한다.**

### Supabase SQL 편집기에 큰 SQL 을 붙여넣지 마라

```
69문항짜리 seed_data.sql 이 조용히 잘렸다. 에러가 안 났다
앞부분(stages 25개)만 커밋되고 문항 구역이 통째로 안 돌았다
클립보드가 개행을 CRLF 로 바꾼다 — 206자 지시문이 214자가 됐다(개행 8개)
```

**해법 셋.**

```
A  필요한 만큼만 잘라 낸 작은 SQL 을 쓰고, 끝에 CR 을 턴다
     update problems set
       instruction = replace(instruction, chr(13), ''),
       passage     = replace(passage, chr(13), '')
     where instruction like '%' || chr(13) || '%'
        or passage     like '%' || chr(13) || '%';

B  psql -f seed_data.sql
   (연결 문자열은 Supabase 상단 'Connect' 버튼. Project Settings 안이 아니다)

C  돌린 뒤 결과 행이 나오는지 본다  ← 잘림을 잡는 유일한 신호(9-5)
```

## 3. 지시문 — 예시를 제 지문으로 쓰면 안 된다

### 3-1. 무엇이 문제였나

세션 7이 넘긴 지시문(225자)은 예시 다섯 줄이 **그 문항 자신의 지문에 독백을 끼운 것**이었다.
곧 그 문항의 모범 답안이다. 그대로 붙여 넣은 답안을 `gradeLocal` 에 넣어 실측했다.

```
예시 = 그 문항 제 지문 + 독백   →  미검출 8/8   아홉 검사가 하나도 안 잡는다
예시 = 중립 장면 하나          →  미검출 0/8   여덟 전부 requireAny 가 잡는다
```

**8/8 은 검사를 더해서 못 막는다.** 붙여넣은 것이 좋은 답안과 같은 글이라
무엇을 세워도 좋은 답안이 같이 걸린다. **인쇄를 안 하는 것이 유일한 수다.**

세션 7 §6 의 3차 줄에 `(다만 모범 답안을 옮겨 적은 것이었다)` 라고 이미 적혀 있었다.

## 5. 덤프 ↔ DB 대조 — `seed_check.sql` (세션 8이 만들었다)

### 5-1. 왜

세션 8 시작 시점에 대조가 하나도 없었다.

```
상수 ↔ 덤프    지시문 일치 가드 8건 · 설정 일치 1건 · 키 가드 8건   있다
덤프 ↔ DB      없었다
```

1장의 셋(404 일곱 · `instr_len 214` · 187자 미반영)을 **전부 잡는다.**

### 5-2. 파일이 넷이 됐다

```
seed_schema.sql   손으로 쓴다
seed_data.sql     자동 생성 · 덤프에서
seed_check.sql    자동 생성 · 덤프에서   ← 신설. 덤프 ↔ DB 대조
seed_verify.sql   손으로 쓴다. 불변식 9건. DB 안에서 닫힌 검사
```

**`seed_verify.sql` 의 `do $$` 블록은 건드리지 마라.** 손으로 쌓은 불변식 9건이고
하나하나가 실제 사고에서 나왔다. 특히 9번(`stage_id` 가 null)은 "오류 없이 조용히
사라진다"를 잡는 그물이다.

### 5-3. 무엇을 대조하나

```
문항 수 · source_key 집합   양방향. 덤프에만 있는 것과 DB 에만 있는 것을 따로 훑는다
instruction                md5 + length
passage                    md5 + length
scoring_config             jsonb 그대로
```

**`md5` 옆에 `length` 를 두는 이유.** md5 만으로는 "다르다"만 알고 무엇이 다른지 모른다.
길이가 함께 있으면 `206→214` 처럼 **CRLF 오염이 즉시 드러난다.**

**`scoring_config` 는 md5 를 안 쓴다.** jsonb 끼리 비교하면 키 순서와 공백이 무관하다.
md5 를 쓰려면 양쪽이 똑같은 정규화 문자열을 만들어야 하는데 배열 표기
(`["a", "b"]` vs `["a","b"]`)에서 갈려 거짓 경보가 난다.

**전부 `is distinct from` 이다.** `<>` 나 `=` 는 null 앞에서 null 을 내고 `where` 가
그 행을 조용히 흘린다. `passage` 가 null 인 문항이 9건 있다
(choice 4 · order 3 · adverb_exception 2). `coalesce` 로 빈 문자열을 씌우지도 마라 —
"null 인 것"과 "빈 문자열인 것"이 구분 안 된다.

### 5-4. `expect` 는 CTE 가 아니라 임시 테이블이다

CTE(`with ... as`)는 **그것이 붙은 문장 하나에만 유효하다.** `do $$` 블록 안의 검사 넷은
각각 별개 문장이라 CTE 로는 못 나눈다 — 69행짜리 `values` 를 네 번 적어야 하고
파일이 85KB 가 되어 잘림 구간에 들어간다.

```
drop table if exists expect;     ← 24행. 앞선 실행이 exception 으로 죽어 남은 것을 지운다
create temporary table expect    ← 26행
...
drop table expect;               ← 정상 종료 시 치운다
```

두 겹이라 **어느 쪽으로 끝나든 재실행이 안전하다**(두 번 돌려 실측했다).

`temporary table` 은 `pg_temp` 에 있어 `anon`·`authenticated` 가 볼 수 없다.
Supabase 편집기가 'destructive / RLS 없는 테이블' 경고를 띄우는데
**`Run without RLS`** 를 누르면 된다. `Run and enable RLS` 는 임시 테이블에 RLS 를
걸려다 검사가 엉뚱하게 죽을 수 있다.

### 5-5. 크기

```
seed_check.sql   22.3KB
잘렸던 seed_data.sql   91KB
```

1/4 이다. 실제로 붙여넣어 통과를 확인했다. 문항이 크게 늘면 다시 재라 —
`scoring_config` 를 md5 로 줄이는 2안이 있다(8KB 로 떨어진다). **지금은 필요 없다.**

**측정 전에 조건부터 찍어라.** 값보다 조건이 먼저다.

(() => {
  const g = document.querySelector('main > div');
  const [l, r] = g.children;
  const d = getComputedStyle(g).display;

        : l.clientWidth === r.clientWidth ? '반반. 정상' : '어긋났다'
  });
})()

### 9-5. 감시가 보이지 않으면 감시가 아니다

`seed_data.sql` 이 잘리는 것을 잡으려고 끝에 `raise notice` 를 넣었다.
**그런데 Supabase 편집기가 NOTICE 를 화면에 안 띄운다.**

```
통과했다        →  Success. No rows returned
잘려서 안 돌았다  →  Success. No rows returned
```

두 상태가 똑같이 보였다. `seed_verify.sql` 의 `불변식 9건 통과` 도 그때까지
한 번도 보인 적이 없었다.

**고침 — 세 파일 모두 마지막 문장을 `select` 로 둔다.** `do $$` 블록은 행을 못 내므로
블록 밖 마지막 문장이어야 한다. `raise notice` 는 지우지 않는다 — psql 경로에서는
그쪽이 보인다.

```
행이 나온다      끝까지 돌았고 통과
No rows         잘렸다
error           어긋난 것이 있다
```

세 파일 전부 통과 행을 내는 것으로 실측했다.

### 9-6. psql 을 먼저 제안했다

붙여넣기가 개행을 바꾸니 파일째 밀자고 했는데, 사람이 새 도구를 깔고 연결 문자열을

길이 두 개면 싼 쪽부터 제시하라.

### 9-7. 지시서에 "54건"이라고 잘못 적었다

덤프의 8단계 외 문항 수를 54로 적었는데 실제는 61이다.
**Claude Code 가 맞추려 고치지 않고 실측치를 그대로 보고했다.** 그것이 정답이었다.
`test:scoring` 을 맞추지 말라는 규칙이 **지시서의 수에도 적용된다.**

### 9-8. Supabase UI 위치를 틀리게 안내했다

`Project Settings → Database` 라고 했는데 거기 없었다. 연결 문자열은
