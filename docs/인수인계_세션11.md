## 0. 세 세션째 비어 있던 탐침이 닫혔다 ★★

```
e_문자열        3    E'가\n나' 는 3자다
생_문자열       4    ★ 3이 아니다. 붙여넣기가 개행을 CRLF 로 바꿨다

거꾸로 추측했고, 세션 10은 그 추측 위에서 고쳤고, **지금 처음으로 직접 쟀다.**

### 그런데 DB 는 깨끗하다 — 이 짝이 요점이다

같은 날 10단계 8문항을 넣고 잰 값이다.

```
탐침    3 · 4 · 2      편집기는 지금도 LF 를 CRLF 로 바꾼다
확인    CR 0           그런데 DB 의 passage·instruction 은 깨끗하다

세션 10이 그 경고를 적어 뒀는데 근거가 이제야 실측으로 섰다.

## 1. 세션 10 §6-1 이 실전에서 처음 걸렸다

`sqlStr` 이 줄바꿈 있는 값만 `E''` 로 내게 고친 뒤로 줄바꿈을 가진 문항이 하나도
안 들어왔다. 10단계 8문항의 `passage`·`instruction` 이 전부 줄바꿈을 갖는다.

```
E'' 리터럴   32 → 48   (+16 = passage 8 + instruction 8)
seed_data.sql CR 0 · DB CR 0 · seed_check 통과
```

`seed_check` 통과가 6-1 이 일했다는 증거다 — md5 가 덤프와 같다.

## 2. 값을 박은 감시와 사실만 재는 감시 ★

같은 세션에서 둘이 나란히 시험받았다.

```
E'' 감시   eLiterals === 32          값을 박았다 → 문항이 느는 첫 순간에 죽었다
겹침 감시   좋은답안최대 >= 베끼기최소   사실만 잰다 → 지문 둘을 갈아도 안 죽었다
```

세션 10이 `실측 32` 를 감시에 박았다. 10단계 8문항이 들어오며 48이 됐고, 등식은
성립하는데(`48 === 48`) `=== 32` 에 걸려 죽었다. **등식만 남기고 절대 수는 주석으로
내렸다.** `=== 48` 을 새로 박지 마라 — 다음 단계에서 또 걸린다.

겹침 감시는 반대로 짰다. 값(7~9)을 안 박고 `겹치는가` 만 잰다. 지문 둘을 갈아
베끼기 최소가 바뀔 수 있었는데 안 죽었다. **값을 박았으면 죽었을 것이고, 그러면
다음 사람이 겹침을 다시 재는 대신 감시를 맞추려고 지문을 되돌렸을 것이다.**

```
감시에 값을 박으면 그 값이 바뀌는 날 감시가 대상을 되돌리게 만든다
사실만 재라. 값은 주석에 남겨라
```

`seed_check.sql` 도 같은 종류다. 세션 10 §2 의 `안 바뀌는 것이 검산이다` 를 좁혀라.

```
md5 는 덤프 문자열에서 뽑는다. SQL 표기만 바꾸면 안 바뀐다   ← 세션 10 이 잰 것
덤프 내용이 바뀌면 바뀐다. 문항이 늘면 바뀌는 것이 정상이다
```

## 3. 병2 정정 — `아직` 이 아니라 `설 자리가 없다` ★

`validateActionItem` 의 지문 꼴 정규식은 안 문다. `passageOf(item)` 이 만든 것을
`passageOf` 의 조건으로 재기 때문이다 — 자기가 만든 것을 자기가 검사한다.

세션 11이 **"덤프 대조가 붙는 날 처음 일한다"고 적었다. 틀렸다.** 덤프 대조를
세우고 덤프 `passage` 에서 `[복선]` 표기를 빼서 재봤다.

```
덤프 ↔ 픽스처 일치   fail   ← 이것이 잡았다
꼴 정규식            통과   ← 여전히 안 문다
```

**덤프 대조는 동등을 잰다. 그것이 꼴보다 세다.** 문자열이 글자 하나까지 같은지
보는 것이 꼴이 맞는지 보는 것보다 강하다. 동등 검사가 있는 자리에서 꼴 검사는
원리적으로 잉여다.

```
지우지 마라. 그러나 물릴 방법을 찾지도 마라. 다음 사람이 또 재게 된다
물릴 수 있는 자리는 validateActionItem 이 외부 문자열을 인자로 받게 될 때뿐이다
```

## 4. 감시가 사람을 잡은 세 번 ★

이 세션 내내 사람 눈이 먼저 잡았다. 세 번은 기계가 먼저 잡았다.

```
known 표시 누락      문서에는 셋으로 세면서 표본에는 known: true 를 둘만 달았다
                    감시를 걸자 8건이 한꺼번에 물었다

bare 파생 설정       requireAny 의존 감시가 { ...AT_CFG, requireInLastLine } 로
                    bare 를 만들어 forbidWords 까지 함께 빼고 있었다.
                    requireAny 하나를 빼는 실험인데 둘을 뺀 실험이었다
                    → 확정값에 키를 더할 때마다 파생 설정을 전수로 다시 봐라

교차 오염            여덟 건이 선 뒤 계속 0이었다. 지문 둘을 갈자 즉시 물었다
                    (창끝 → at-cracked-ice). 자리가 비어 있던 게 아니라

**0을 '빈 자리'로 읽지 마라.** 0이 나오는 감시가 셋인데 성질이 다르다.

교차   물 조건이 안 왔을 뿐이다      ★ 살아 있는 감시다
```

이것이 감시를 늘리는 이유다.

## 5. 사람에게 보내는 것이 세 번 샜다

세션 10 §8-2 가 `붙여넣기 한 번으로 끝나야 한다` 를 적어 뒀다. 세 번 어겼다.

```
1  패치 안의 CR 12개가 붙여넣기로 안 건너갔다 → git apply 거부
   ★ CR 이 든 파일은 붙여넣기가 아니라 파일로 건네라
2  git commit -F <메시지> 를 자리표시자로 보냈다 → 셸이 통째로 실행
   ★ heredoc(<<'EOF')을 완성해서 보내라. 자리표시자를 쓰지 마라
3  한글 파일명이 전달 경로에서 깨져 파일이 안 열렸다
   ★ 파일명을 ASCII 로 내라. 파일 내용의 한글은 괜찮다 — 깨진 것은 이름뿐
```

그리고 더 나쁜 것이 하나 있었다.

```
패치가 안 붙어도 test:scoring 이 1556/0 으로 같았다
그 수를 확인 절차에 넣어 두어 하마터면 통과로 볼 뻔했다

★ 패치가 붙었는지는 test:scoring 으로 확인할 수 없다
  git status --short 와 내용 grep 으로 확인해라
```

이 세션 내내 `같은 수가 검사가 일한다는 증거가 아니다` 라고 해 놓고 같은 자리에서
걸렸다.

## 6. 일의 나눔은 권한으로 갈린다

```
Claude(대화)   근거를 재고 값을 정하고 지시서·SQL 을 만든다. 저장소를 읽는다
Claude Code    저장소 코드를 고친다. DB 자격증명이 없고 브라우저도 없다
사람           SQL 을 Supabase 에서 직접 돌린다. 화면을 보고 답안을 쓴다
```

**'클로드 코드'는 역할 이름이지 도구 이름이 아니다.** 이 세션의 마지막 두 커밋은
사람이 터미널에서 같은 명령을 쳤고 결과가 같았다. 갈리는 것은 권한이다 — DB
자격증명은 사람에게만 있다.

다만 잃는 것이 있다. 클로드 코드가 하면 병 시험을 스스로 재현해 보고한다.
터미널로 하면 그 확인이 빠진다. 그때는 **푸시 뒤 블롭 대조**가 유일한 확인이다.
이 세션은 네 커밋 모두 그렇게 확인했고 네 번 다 일치했다.

## 7. 자료의 범위를 착각했다 ★

세션 10 §7-1(1) 이 `턴제 액션` 을 **'자료 7종·설계서·ch0*.json 어디에도 없다'** 는
근거로 `전투 서사화` 로 바꿨다. 그 근거가 틀렸다.

```
정리본(웹소설_작법_정리*.md)   턴제 0건. 세션 10 이 본 것은 맞다
정리본 밖 원자료(영상 넷)      '웹소설 전투는 턴제이다' — 명시로 있다
```

**정리본은 요약이다. `정리본에 없다` 는 `자료에 없다` 가 아니다.**

결론(title 변경)은 살아남고 근거가 세진다. 같은 원자료가 셋을 순위로 놓는다.

```
3위  턴제                     전투의 형식
2위  행동이 아니라 행동의 의도   수싸움
1위  감정                     내가 상대방을 이겨야만 하는 이유
```

단계 이름이 3위에 붙어 있었다. 그리고 1위(2부 23-1)를 설계서가 난이도 2·3에
배정했다는 것이 `source` 표기로 확인됐다 — 자세한 것은 지문 요건 문서 0장.

**원자료를 이 세션에서 처음 읽었다.** 정리본만 보고 열한 세션이 지났다.
다음 사람은 정리본에 없는 것을 없다고 결론짓기 전에 원자료를 찾아봐라.

## 8. 다음 자리는 AI 심사다 — 첫 측정 표본이 이미 섰다 ★

`scoring_mode` 는 `auto` 로 넣었다. 덤프 85문항 중 `hybrid` 는 `emotion_action`
6건뿐이고, 8문항 단계 넷이 전부 `auto` 다. 그리고 **AI 심사 코드가 아직 없다** —
`needsAi` 는 화면에 표시만 낸다(`TrainClient` 주석이 그렇게 적혀 있다).

```
지금        auto
안 하는 것   토큰이 있으니 미리 hybrid 로 박아 두기
            ★ 토큰이 있는 것과 심사가 서는 것은 다르다
            없는 것: 심사 코드 · 프롬프트 · 골든셋 기준 · 오탐 측정 · 하니스
바뀔 조건    심사가 서고, known 넷을 실제로 잡는지 재고, 좋은 답안 오탐을 잰 뒤
            그때 10단계가 첫 후보다 — 규칙으로 원리적으로 못 잡는 자리가 넷 있다
```

### 표본 288건이 이미 서 있다

```
known 넷    낱낱 나열 · 빌드업 없이 압축 · 지문의 결정타 줄을 그대로
            (난이도 2 전용) 복선을 한 번도 안 씀

재는 순서는 이 세션이 규칙에 대해 한 그대로다.

```
1  known 넷을 AI 가 잡는가                    미검출
2  좋은 답안 144건에 오탐이 나는가              ★ 이쪽을 안 재면 규칙 때와 같은 병이다

5  표본이 요건을 건드리는지 봐라 — 안 건드리면 오탐 0이 표본 선택의 결과다

2번이 가장 중요하다. 이 세션이 밴드에서 겪은 것이 정확히 그것이다.
